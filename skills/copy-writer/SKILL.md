# Copy Writer Skill

来源：`docs/产品设计/simple-skill-pipeline-四类规则归一.md`  
版本：当前确认版本  
定位：按 Copy Skill 责任拆分后的运行输入与接口规范；内容业务规则仍追溯到 `rules/01—06`，不构成第二套并列业务规则。

真实调用入口：`app/server/simple-copy-skill.mjs` 的 `runCopyWriterSkill()`。

## 1. Purpose

在 Planner 已经确定模块、事实、正式状态和写作目标的前提下，生成符合奢游品牌要求的客户文案。允许在可追溯事实边界内真实丰富表达；不决定产品结构，不虚构事实或承诺。

## 2. When to use

用于批量或单项生成：

- 封面主标题、封面副标题；
- 产品亮点；
- 行程总览；
- 酒店总览；
- 特色餐饮；
- 全程交通；
- DAY 文案与今日贴士；
- 费用、注意事项、定制师等客户文案。

不得用本 Skill 决定模块是否显示、页面结构、模块顺序或图片选择。

## 3. Input Contract

接受批量 `tasks[]`，整批可包含 `itineraryContext`，例如：

- `destination`
- `dayCount`
- 整程内容主线与必要上下文

每个 task 至少包含：

- `targetId`
- `moduleType`
- `facts`
- `factStatuses`
- `plannerGoal`
- `relevantContext`
- `layoutHints`（仅必要时）
- `targetPath`
- `outputSchema`

`targetPath` 是当前客户行程数据根对象下的精确点路径，例如 `highlights.0`、`hotels.0.editorialCopy`、`hotels.0.proofPoints`、`days.2.theme`、`days.2.description` 或 `days.2.spots.0.description`。`outputSchema` 是与当前 itinerary schema 相容的 JSON Schema 片段，定义该路径所需的值结构。输入事实与状态是不可覆盖约束；状态不得在措辞过程中被抹去或升级。

每个 task 可选包含 `researchRequest`。没有该字段时直接进入 Copy Writer，不得联网；存在时只允许 `official_entity_facts` 或 `authoritative_current_facts`，先由 Copy Skill 内部完成事实研究，再把 `{researchType, entityName, verifiedFacts:[{category,fact,sourceUrl,sourceExcerpt,checkedAt}]}` 作为内部证据交给 Writer。研究不是新顶层阶段，失败只影响声明该请求的目标，证据不得进入客户文案。官方实体事实仅采用实体/品牌/官方组织来源；时效事实仅采用政府、使领馆、正式组织或正式运营方来源。第三方网页和图片不得自动成为 `verifiedFacts`。

产品亮点任务必须已经由 Planner 逐项确定，并包含稳定 `targetId`、精确 `targetPath`、既定卖点事实与来源、写作目标及输出结构。如果亮点任务缺少这些责任信息或要求本 Skill 重新决定亮点集合，返回明确接口问题，不自行规划。

## 4. Batching

- Planner 产生多个逻辑任务，不等于多个物理模型调用。
- 必须支持批量输入和按 `targetId` 独立返回。
- 标准 7—10 日行程的 DAY 文案优先批量生成；可按模块性质合理合批。
- 当前标准物理批次为三类：全局文案/亮点/酒店/交通、全部 DAY、notes 结构化任务；某类无任务时不产生空调用，不拆成逐 DAY 调用。
- 每个物理批次遇到空正文、JSON 异常或网络错误时只允许一次技术重试；技术重试不进入 Planner、Reviewer 或业务 retry，某批失败只影响该批 targets。
- 批量生成仍须保持每个 DAY 的事实边界、独立重点和前后叙事关系。

## 5. Writing Rules

### 5.1 品牌表达与事实边界

- 任务 facts 已提供 `displayName`、`displayNames[currentLocale]`、`shortName`、`entityDisplayName` 或其他已解析实体展示名时，所有客户可见标题和正文必须优先、原样使用该名称；不得重新展开 `officialName/canonicalName`、重新翻译、自行音译或创造新的中文实体名称。当前 locale 没有展示名时保留 canonicalName，不猜测翻译，并保留 `entity_display_name_missing` 供程序处理。客户展示名不得反向用于 Facts Research、Image Search、知识库精确查询或 `searchIntent`。
- 结构数据负责完整，Copy 负责选择。客户文案不是源资料、Planner facts 或 `verifiedFacts` 的完整摘要；先判断当前模块要回答的客户问题，再选择最值得客户看到的少量事实。
- 每段只突出一个主价值，必要时增加一个辅助价值。真实但与当前模块核心客户问题无关的事实可以不进入正文，不得用“完整复述”代替内容判断。
- 角色定位是“高端定制旅行产品内容营销写作者”，不是供应商资料复述员、百科编辑、官网翻译员、旅行散文作者或口号生成器。
- 先制造向往，再呈现稀缺价值，再说明具体安排，最后专业说明边界。
- 保持热情、从容、专业和有画面感，优先写客户可感知的场景、动作、节奏和旅行价值。内容丰富度来自“真实事实 + 合理体验化展开 + 客户价值”，不来自形容词、隐喻或情绪堆叠。
- 每句话至少完成一项职责：A. 提供事实；B. 解释体验如何发生；C. 说明对客户的价值。连续形容词、隐喻和情绪句如果不承担任何一项职责，属于低信息量文学化表达。
- “荒野注解、低语世界、触摸脉搏、正确打开方式、震撼”等散文化套语如果没有新增事实、体验方式或客户价值，必须删除，不得用来填充篇幅。
- 避免供应商流水账、说明书、百科腔、翻译腔、廉价促销和用空泛形容词代替内容。
- Copy 不是只能逐字复述 Excel。可基于已确认地点、活动、酒店、住宿形态、交通方式、节奏与服务方式，合理说明客人会怎样体验、这种安排带来什么体感和为什么值得；只要不改变产品边界，不要求 Excel 存在完全相同原句。
- 客观可核验事实只能使用原始已确认资料、用户/正式供应商确认、确定性配置或任务输入中的 `verifiedFacts`。公开研究只能补充实体客观是什么、有什么，不能推断本订单购买了什么。
- 真实补充必须依附明确实体与可核验背景，且不能覆盖或改变原始事实。酒店星级/等级/品牌定位、设施、位置、奖项、固定活动时间、保证看到的动物、具体人员资质、车型、房型、菜单、开放时间和运营规则等具体事实必须有可追溯来源；任务输入没有依据且无法稳定确认时不写。
- 判断一句话是否可用，要看它有没有新增未经支持的客观承诺、履约事实或订单边界，而不是检查某个词是否出现在 Excel。基于已确认活动作合理体验展开、不固定具体钟点的时间推进、已确认 guided activity 中对向导和观察方式的自然表达、已确认夜间游猎中的常规探照观察方式、非保证性的动物观察表达，以及不改变订单状态的轻量预约建议，都允许使用。
- 只有固定钟点、保证看到具体动物或获得某结果、具体人员资质等级、强制预约要求或精确预约期限、具体金额，以及“已包含、已预订、保证使用某房型/车型”等会改变产品事实和客户承诺的表达，才必须在当前 task 的订单事实或 `verifiedFacts` 中有明确依据；不能从相邻 DAY、其他模块或模型常识借用。“建议提前咨询/预约，以实际确认为准”属于轻量建议；“需提前预约/必须预约”会改变订单要求，必须有 `reservation_required` 等确定性状态支持。
- 野生动物可以写作目的地语境、常见观察对象或“有机会观察”等非保证表达；不得把“可能看到”写成“保证/必然看到”，不得保证天气、迁徙、渡河、升级、包场和未确认体验。
- 禁止虚构不存在的设施、服务或活动；禁止修改价格、交通承诺、接待等级、服务等级及其他履约边界。
- 房型、包含项、价格、已保证车型、已预订服务和正式状态只能服从 Excel、用户确认、正式供应商确认或确定性配置；实体官网的一般性信息不能证明本次订单已购买或包含。
- 已含、自费可选、需预约、待确认和需核验等状态必须真实，并与费用边界一致。
- 成本、底价、利润、公式、供应商内部备注、模型提示词和审核信息不得进入客户文案。

### 5.2 封面

- 主标题使用“目的地 + X天X晚 + 产品形态”，不写人数，不用“定制团/私家团”冒充产品形态。
- 不设 24 字硬门槛，以实际版面单行可读和是否溢出为准。
- 副标题是一条整程销售叙事，回答“这是一条怎样的旅程、核心体验组合是什么、最终形成怎样的旅行结果”。优先从 Planner 整程主题、来源指定亮点、DAY role 中最有辨识度的 2—3 个整程锚点及最多一个重要配置中选择，不把全部地点、酒店、交通和体验列成摘要；控制为 2—3 行且不超过 76 字。

### 5.3 产品亮点

- Planner 负责最终确定实际采用的产品亮点集合：目标为 5—7 条，真实资料不足时按既定规则保留可支持的真实条数；本 Skill 只逐项写好 Planner 已确定的亮点。
- 不得自行新增、删除或重新筛选亮点，不得重新决定亮点优先级，不得把普通 DAY 细节提升为产品亮点。
- 忠实承接每条任务中既定的来源、事实和卖点含义，不自行改变来源层级或创造品牌承诺。
- 每条必须使用“短标题 + 具体客户价值说明”，解释为什么它让整条产品更值得选择；不能只写体验名、酒店名、服务名或关键词。
- 一条亮点只讲一个购买理由。标题负责记忆，正文只解释这个理由为什么重要，不继续叠加第二、第三个独立卖点。
- 短标题简洁、有记忆点但有实际含义，正文承担完整价值表达。
- 如果 Planner 传入的产品亮点任务不符合接口要求，返回该 `targetId` 的 `needs_input` 和明确接口错误，不自行重新规划产品亮点。

### 5.4 行程总览与 DAY 主题

- 行程总览清楚说明整程走向、DAY 主题、路线和确实影响体感的交通信息。
- DAY 主题是当天最值得记住的一句话钩子，不是全日摘要。从 `dayRole`、相邻日差异和当天真实体验中选 1 个主记忆点，最多带 1 个辅助点，写成标题式短句。
- “抵达、转场、返程”等动作不能单独充当主题，但与当天独特体验或旅行变化结合时可以使用，例如抵达后的第一眼体验、转场带来的区域变化或返程后的城市收束。

### 5.5 酒店总览

回答：这家酒店在这趟旅行里最值得期待什么。酒店自身住宿价值为主，产品角色为辅；从真实信息中选择 1—2 个最能建立住宿期待的空间、景观或居停锚点，可用一句短表达说明旅程开场、深入区域、连住节奏或城市收束等产品角色。

- `editorialCopy` 使用 2—4 句直接陈述：先说明酒店是什么及位于哪里，再选择 1—2 个真实住宿特点并解释客户价值，最多用一句说明整程产品角色。每句话只承担一个主要功能，少用长并列句，不用比喻、拟人或情绪化收尾替代信息。
- 不要求解释为什么路线安排住这里、对前后路线有何作用或如何承接某个 DAY。
- 不写设施清单、供应商宣传、翻译腔和无依据奢华形容。
- 酒店正常生成路径是：酒店名称 → Copy Facts Research 搜索实体官网、品牌官网或母品牌官方页 → 程序核验来源 → `verifiedFacts` → Copy 从中选择最有价值的 1—2 个事实 → 转换成客户住宿价值表达。`verifiedFacts` 是酒店外部客观事实的主要来源和候选素材池，不要求全部写进正文。
- `editorialCopy` 与 `proofPoints` 只使用当前酒店的订单事实、原始供应商资料中明确属于该酒店的事实和 `verifiedFacts`；游猎、向导、动物追踪、当天出门与归来不属于酒店总览，除非它们本身是当前酒店已有来源的正式服务或体验事实。
- 存在 `researchRequest` 但最终 `verifiedFacts = 0` 时，必须记录“酒店官方事实研究未成功”，不得依赖模型常识新增酒店设计、设施、景观、服务或房型事实。只能选择原始供应商资料已明确提供的酒店事实；如果原始资料也只有酒店名、地区、晚数等极少信息，正文保持非常克制或返回事实不足 warning，不能让产品角色取代真实酒店事实，也不能生成泛化酒店介绍。
- `editorialCopy` 负责解释住宿价值，不做官网摘要或设施清单。
- `proofPoints` 负责快速记忆：正常输出 2—3 个短标签，优先选择真实地点、保护区、景观、空间类型、明确数量或客户一眼能理解的住宿价值。每项只表达一个事实或价值，优先 4—10 个中文字，不写完整说明句，不以“位于、拥有、提供、配备”开头，不用抽象修辞包装事实，也不重复正文完整句。事实只支持 0—1 项时按真实数量返回并说明事实不足，不得凑满；最多可有一个轻量产品角色标签。
- 不设最小字数；体验锚点字数仅可作为模板适配参考。
- 具体入住日、抵达情境和当天衔接由 DAY 表达。

### 5.6 特色餐饮总览

- `diningExperiences` 是 Program 已从真实候选中选出的整程代表体验，不是关键词全集；Copy 不重新选择、不恢复被排除的普通餐食、重复同类项或附属于其他主体验的餐食。
- Dining 是特色美食、品饮和特殊用餐体验的产品介绍，最终回答“这一顿和普通用餐有什么不同，为什么值得期待”，不是以风景、氛围或情绪为主体的旅行散文。
- 每项优先用一个完整短句，确有必要时最多两句。正文优先顺序为：餐饮类型或品饮内容 → 怎么吃、怎么喝或怎么品 → 味觉/品饮/用餐方式的特点 → 已确认的特色场景 → 一个直接客户价值。无需机械覆盖全部五层，但餐饮本身必须先于场景和情绪被客户看懂。
- 本模块不以全局“先制造向往”作为写景开头；向往必须从餐饮内容和体验方式本身产生。第一句以吃、喝、品、早餐、晚餐或明确餐饮类型为语义主体。即使删除场景和氛围修饰，客户仍应看懂吃什么或品什么、怎样体验，以及它与普通用餐的差异。
- 优先采用“餐饮动作或内容 → 已确认的体验方式/场景 → 与普通用餐的直接差异或价值”的产品句式。每个分句都必须回答餐饮是什么、怎样体验或为什么特别；餐饮信息已经完整后，不再增加只用于总结旅程、情绪或记忆的尾句。
- Dining 不承担当天或整趟旅程的收束职责。餐饮信息与直接价值写清后立即结束，不需要总结一天、告别一地或为旅程收尾。
- “有体验感”是让客户理解怎么吃、怎么喝、怎么坐下来体验，以及为什么这顿与普通三餐不同。允许使用场景感、氛围感和记忆感，但它们只能增强餐饮主体；不能用写景、抽象情绪或诗性收尾代替餐饮内容。
- 客观事实必须有依据；可基于已确认的餐饮类型、地点、场景与安排做通常语义范围内的自然动作展开，不要求 `sourceEvidence` 出现完全相同原句。自然展开不能新增具体菜单、食材、酒款、设施、人员、布置、制作方式或服务流程等可独立核验的现场事实。
- `facts.copyGuidance` 是 Planner 根据当前餐饮类型给出的本项价值方向与负面边界，必须逐项遵守；它不新增客户事实，也不能用于恢复被 Program 排除的 Dining 候选。
- 卡片已展示 `title`、`location` 和 `status`，正文直接从体验方式切入，不以完整 `title`、`officialName` 或 `location` 再次命名卡片，也不机械重复 DAY 编号及“已包含/自费/待确认”等状态说明；体验类型中的通用词可以自然使用。局部升级收费只作为事实边界，不在总览正文反复强调，也不得暗示升级消费已包含。
- 普通早餐、午餐、午餐盒和普通酒店晚餐只在 DAY 中简洁表达。体验若只是另一项主体验的组成部分，不得由 Copy 升级成独立餐饮卡。
- 直接客户价值优先落在味觉或品饮重点、用餐方式、体验节奏及当天衔接。不得借用同批其他 Dining target 的事实，不设最小字数。
- 具体体验日、当天展开和局部费用边界由 DAY 表达。

### 5.7 全程交通总览

- 每张交通卡按现有字段承担五层职责：`usageLabel` 说明主要用在哪里；`category` 说明客户实际使用什么；`serviceLevel`、`seatCount` 与有保证的 `model` 用作配置/产品角色短标签；`editorialCopy` 只解释一个核心客户价值；`features` 给出 2—3 个真实、短而易懂的配置价值点。标题与标签不得原样重复，真实信息不足时宁可少一层或少一条，不得凑数。
- `usageLabel` 从 `usageSegments` 与当前交通事实概括真实城市、区域、保护区或衔接场景，不输出 DAY 编号和未经整理的内部路线字符串。
- `features` 只能选择当前任务事实支持的座位/承载、开顶结构、真实使用方式、已确认包含状态或移动价值；不能把一般交通百科、未确认行李规则或未经结构化确认的包含项写成本产品配置。
- 没有来源时不自行补座位空间、动力、准时性、车型能力或精确节省时间；有依据的配置只在确实有助于解释当前唯一客户价值时选择使用。
- 不逐段展示内部 DAY 路线映射或解释每一段 A→B。
- 具体日期、起讫地点和当天乘坐方式由 DAY 表达。
- 没有明确车型保证时不得承诺具体车型，不设最小字数或关键词命中要求。

### 5.8 DAY 文案

- 站在高端定制旅行产品经理视角组织 DAY，正文回答“今天最核心的一段体验怎么展开”。普通 DAY 从真实事实中选择 1 个主体验、最多 1 个辅助体验，用必要移动信息串联并解释为什么值得；结构字段负责完整保存路线、交通、餐食、住宿、Spot、状态与费用边界，正文不逐项复述。
- 相邻 DAY 必须依据 Planner `dayRole`、差异说明和真实事实形成不同重点，不能把同一地点或“游猎日”批量同义改写。
- `days[].description` 负责整日推进、主次关系和整程承接；`days[].spots[].description` 只解释对应 spot 的内容、体验方式与客户价值，不得复制整日摘要，也不得改写 spot 名称、状态、费用边界、可选性或来源证据。
- 同名 spot 跨日出现时，结合本日 `dayRole` 调整信息重点或保持克制，不得复用相邻日整句；spot 卡不得带入酒店、当日其他活动或整日收束。即使原始 `sourceEvidence` 是混合了多项安排的整日短句，也只提取与当前 spot 名称直接相关的活动事实。
- 不只写“前往—参观—返回”；可以使用不形成固定钟点承诺的合理时间推进，具体履约时刻必须有订单或已核验依据；百科信息要转成客户现场体验。
- 普通体验日优先约 120—180 字且宜不超过 220 字，纯转场/返程日优先约 80—130 字；均为软建议，不得仅因超出而失败、删除或重生成。
- 普通体验日最多 5 句、转场日最多 3 句仅作写作参考，不是失败条件；不设 46/24 字最小值。
- 酒店、特色餐饮、交通或来源指定亮点可在总览/亮点与 DAY 跨层表达，但角度和粒度必须不同，不得整句整段复制。

### 5.9 Spot 体验卡

- Spot 只负责当前单个体验，用 1—2 句说明这项体验怎么发生、为什么值得；不总结整天，不借入酒店、餐食、交通或其他 Spot。
- 同名 Spot 有真实区别时写区别；没有真实区别时保持简洁，不机械换词或制造不存在的细节。
- 不改写 Spot 名称、状态、费用边界、可选性和来源证据。原始证据是混合整日描述时，只使用与当前 Spot 直接相关的事实。

### 5.9.1 DAY Visual Card 短描述任务

- `moduleType=visual_card` 是现有 DAY 批次中的独立文案任务，不是图片搜索指令，也不是可以省略的内部元数据。必须逐个返回原始 `targetId`、`targetPath` 和对象 `value:{cardTitle,cardDescription}`，即使视觉主题没有同名 Spot。旧任务若明确要求字符串则遵守该任务 outputSchema。
- `simpleImageSlotBindings.<bindingKey>` 是合法的内部文案写回位置；不要因为它不以 `days.` 开头而忽略、改路径或把结果合并进 DAY/Spot 正文。
- 只围绕该任务 `facts.visualSubject`，根据本日 `daySourceFacts` 和 `sourceEvidence` 写 1—2 句：怎样体验、为什么值得。不总结整日，不复制其他视觉卡或泛化 Spot 描述，不从相邻 DAY 借用事实。
- cardTitle由本次Copy生成，必须是短而直接的旅行体验名称，如“步行 Safari”“Naboisho 私保区追踪花豹”“星空床”“长颈鹿中心互动”；不是照抄primaryVisualSubject的画面描述。不要把“一只花豹栖于树上”“跑道飞机起飞与晨光”等姿态、构图和光线细节写成客户标题，除非本身就是体验核心。不改视觉主题、不新增体验。任务 facts 提供 `entityDisplayName` 时，标题必须原样包含该名称，不得把同一实体重新翻译成另一种中文名；这不改变 `searchIntent`。
- cardDescription写1—2句简短体验说明。客户卡片只显示图片、cardTitle和cardDescription，不输出单独的状态/费用标签。保留事实费用和可选边界，不暗示未购买的体验已包含，不把观察动物或天气写成保证。cardTitle和cardDescription不参与搜图，也不决定Image输入。
- 输出前核对输入的每一个 visual_card target 都有独立结果；不能仅返回原有 DAY 和 Spot 文案。

### 5.10 其他模块与辅助检测

- 今日贴士回答“提前知道什么会让当天更顺”，每天最多一条；没有真实准备价值时不生成，不为页面整齐强制每天都有。原始资料有明确当天提醒时保留原意与 `sourceEvidence`；没有直接提醒时，只能依据当前 DAY 已确认的活动、交通、移动、天气敏感体验或正式状态生成。
- 今日贴士 Copy 只允许写 `days.<index>.dayNotices.0.text`。可写穿着、装备、节奏、身体准备、草原飞机出票后核对行李要求、热气球较早准备、夜间体验增减衣物或自费体验提前确认；不得新增政策事实、费用、订单包含、预约状态、服务承诺、精确时间、酒店设施、无来源行李重量/尺寸数字或动物出现保证。
- 涉及 eTA、签证、疫苗、航空行李额度、门票政策或开放时间，只有当前任务输入已有原始事实或 `authoritative current facts` 时才能写具体要求；否则只说明以出票或出发前最终确认信息为准。全程注意事项不得复制进 DAY，语言简短、服务型，不写“警告、务必、严禁、请注意风险”等命令或免责口吻。
- 注意事项定位为“定制师提前替客户想到的暖心提醒”，不是警示说明。每条先表达服务团队已经提前考虑或将协助核对的事项，再给客户一个具体准备动作；需临近出发确认时，明确由定制师协助核对，不把责任单独推给客户。
- 服务型语气不能升级为无来源承诺：不得声称已经掌握输入中没有的客户偏好、健康情况或纪念日，也不得承诺未配置的供应商资质、布置、顾问服务或全部项目已确认。
- 注意事项标题使用出行准备、健康与安心、当地文化与礼仪、出发前再确认等服务型语义；安全事实改写为跟随向导和现场安排即可执行的安心建议，不写成命令、免责或营销软文；不为了“完整”硬塞所有类别。
- 旅行准备与注意事项是固定必需模块。原始资料没有 notes 时，必须依据任务提供的已确认事实、目的地、路线、活动和旅客信息生成 `{title, items[], tone?}[]`；时效信息无正式来源时仅提示行前核验，不虚构政策、天气、健康或安全结论。
- 未取得权威当前事实时，不输出具体政策有效期、金额、固定健康要求，只说明定制师将在出发前按最新正式信息协助核对；也不输出“营地通常提供洗衣、卫星电话或 Wi-Fi”等泛化酒店服务结论。
- 定制师只使用真实配置；无资料时使用明确的非真人默认身份，不编造业绩和联系方式。
- 供应商语气关键词、文本相似度、建议句数、软字数和流水账句式只能辅助判断，不能单独阻断。
- 不得恢复 DAY 46/24 最小字数、DAY 5/3 句硬失败、DAY 220/130 字硬失败、酒店 34 字最低、交通 24 字最低、相似度数值硬门禁或 Reviewer 自动重写。

## 6. Output Contract

整批返回：

- `status`: `success | partial_success | needs_input | failed`
- `results[]`: 按 `targetId` 独立对应 Planner 任务
- `researchResults[]`: 仅记录声明了 `researchRequest` 的目标及内部 `verifiedFacts`，不得进入客户字段
- `warnings[]`: 记录不影响其他任务继续的问题

每个 result 至少包含：

- `targetId`
- `targetPath`
- `status`
- `value`（成功时；必须符合该 task 的 `outputSchema`）
- `warnings`（如有）
- `error` 或 `missingInput`（失败或需输入时）

返回的 `targetPath` 必须与输入 task 完全一致，不能由 Copy Skill 改写。整批 `status` 只汇总批次结果，不得抹去单项状态。产品亮点接口不完整时使用 `needs_input`，并返回 `error.code = "invalid_highlight_contract"` 及缺失或冲突字段。

Program 在接受成功值前执行确定性承诺边界门禁：只拒绝当前任务没有依据、且会新增产品事实或客户承诺的固定钟点、保证性结果、具体人员资质等级、强制预约要求或精确预约期限、具体金额、订单包含/确认状态及具体房型或车型承诺，返回当前 target 的 `unsupported_copy_commitment`。该门禁不按“清晨/傍晚、动物、向导、探照灯、预约、游猎、徒步、管家、公共空间、泳池、露台/凉亭、房型/住宿空间”等类别词直接拒绝；这些内容的事实质量由 Copy 输入事实、`verifiedFacts`、写作约束和人工审查保证。门禁不承担普通文风或实体设施逐词核验，无模型调用、不改写文案、不触发 retry。

## 7. Failure Semantics

- 一个 target 失败，只返回该 target 失败，其他成功结果必须保留。
- 例如 DAY6 失败，只标记 DAY6；DAY1—5、DAY7—10 的结果继续保留。
- 不得自动重生成整批、重生成其他已成功模块、进入 Reviewer 或 Agent 修复闭环。
- 空返回、JSON 异常、请求异常等技术问题由 Program 技术层处理；本 Skill 不建立业务 retry 闭环。
- Copy Facts Research 的空内容或畸形 JSON 最多允许一次传输级技术重试，并单独计入 `researchTransportAttempts`；逻辑 `researchCalls`、Copy Writer `modelCalls` 与 `automaticBusinessRetryRounds` 必须分开记录。

## 8. Forbidden

禁止修改确定性事实、费用状态或体验状态；禁止决定模块显示、模块顺序或页面结构；禁止搜图；禁止 `review_decision`、finding package、Reviewer 和自动多轮重写。

`simple-skill-pipeline` 同时不启用多层 Reviewer、Reviewer 发现问题后自动重生成、stage budget 驱动业务流程、98% 完成状态，以及单个目标失败导致整批或整阶段重跑。
