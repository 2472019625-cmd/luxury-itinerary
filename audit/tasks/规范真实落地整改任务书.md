# 奢游行程工具规范真实落地整改任务书

更新时间：2026-08-29

依据：`AUD-014`、`AUD-015`、`AUD-016` 及 `audit/evidence/2026-08-29-rule-implementation-audit/01-rule-implementation-matrix.md`。

## 一、整改目标

本轮不是简单增加几句提示词，而是让关键规范形成真实执行闭环：

> 原始事实完整进入程序 → 模型收到正确规则和字段 → 返回结果被保存 → 程序检查结果 → 不合格时只重做问题位置 → 真实任务和自动测试证明生效。

需要解决：

1. 自费、可选、待确认体验可以作为卖点和主图，但状态与费用边界必须清楚。
2. 每日文案恢复奢游表达，不再是供应商式流水账。
3. 模型返回的每日路线、节奏、体验点不能再被程序丢弃。
4. 每日图片由完整内容和整份图片故事决定，不再机械地一天一个图片位。
5. 原始资料遗漏、酒店晚数、交通、费用和体验状态冲突能在生成前发现。
6. 2000px 成品复查从“只看图片”扩展为“图片、文案、状态、费用和版面共同检查”。

## 二、必须保护的现有功能

以下功能本轮只做回归保护，不得推倒重写：

- Excel 上传、解析和确认页；
- 日期连续映射、人数显示、返程住宿判断；
- 整程图片蓝图、真实搜索、下载、本地保存、严格终审和全局去重；
- 生成完成后直接进入编辑器；
- 编辑器换图弹窗、跨模块移动、本地上传、单位置重搜和用户锁定；
- 真实进度、阶段、耗时和统计；
- 保存、刷新恢复、版本历史和 2000px PNG 导出；
- 固定品牌页尾、定制师资料和现有长图视觉样式。

图片终审门槛不降低。增加图片位不等于强行填满；没有合格图时仍允许留空。

## 三、总体实现方式

保持当前单体项目结构，不引入复杂工作流平台。新增一个客户内容提示词文件和一个内容质量检查模块即可：

- `app/prompts/customer-itinerary-editor.md`：工具内文案模型真正读取的核心规范。
- `app/server/content-quality.mjs`：生成后确定性检查、问题定位和局部重写入口。
- 现有 `app/prompts/image-blueprint-planner.md`：继续负责整份图片故事，但按本任务书更新。
- 现有 `app/src/lib/itineraryRules.js`：继续负责日期、人数、夜宿等确定性事实，并补充跨板块一致性检查。

不要让运行时临时读取整份 `AGENTS.md` 或所有说明文档。运行时只读取专用提示词和统一规则模块，避免规则过长、相互冲突和难以测试。

## 四、第一批：先修数据骨架和规则冲突

这一批完成前，不开始扩充每日图片数量。

### 4.1 建立统一体验状态

每日 `spots` 至少保留：

```json
{
  "id": "稳定ID",
  "name": "体验名称",
  "description": "客户版体验说明",
  "status": "included | optional_paid | reservation_required | pending",
  "statusLabel": "已包含 | 自费可选 | 需提前预约 | 待确认",
  "feeBoundary": "included | excluded | pending",
  "sourceEvidence": ["原始事实依据"],
  "images": []
}
```

要求：

- 状态优先来自原始表格和确认页，不允许模型凭空决定。
- 自费、可选、待确认体验允许成为主 `spot` 和主图。
- 客户卡片使用安静状态行显示状态，不恢复图片角标。
- `optional_paid` 必须能在费用不含中找到对应项；`pending` 必须进入待确认信息。
- 用户确认购买后，才将状态改为 `included`，同时从费用不含移除。

### 4.2 修正两个模型的旧限制

修改：

- `app/server/app.mjs`：删除“自费、可选或未确认项目不得进入 spots”。
- `app/server/image-blueprint.mjs`：删除按未包含状态直接拒绝高优先级主图的逻辑。
- `tests/image-pipeline.test.mjs`：把旧测试改为验证“允许作为主图，但状态和费用边界必须一致”。
- `app/prompts/image-blueprint-planner.md`：保留本次已经确认的新口径。

### 4.3 把完整事实发送给客户文案模型

`compactForModel()` 增加：

- `included`、`excluded`、`cancellation`；
- 酒店房型、餐食、确认/参考/替换状态；
- 交通等级、座位数、车型和 `modelGuaranteed`；
- `spots` 的 `status`、`statusLabel`、`feeBoundary`、`optional`、`confirmed` 和事实依据；
- 客户偏好、特殊需求和导入阶段产生的待确认信息。

不得把成本、利润、供应商底价或内部操作备注发送给客户文案模型。

### 4.4 修复模型结果被丢弃的问题

`mergeRefinement()` 按同一 `day.index` 合并并保存：

- `theme`；
- `routeNodes`；
- `estimatedTravelTime`；
- `activityLevel`；
- `restStops`；
- `overnightType`；
- `spots`；
- `description`；
- 最多一条 `dayNotices`。

合并规则：

- 日期、天数、原始路线、酒店晚数、餐食、交通和费用状态以确定性事实为准。
- 模型只能重写表达和拆分体验，不能改变事实。
- 返回缺字段时保留原数据，不得用空值覆盖。
- 返回多天、少天、重复 index 或跨天内容时拒绝本次每日结果。

### 第一批验收

1. DAY 3 徒步、DAY 4 热气球等自费体验允许成为主图规划对象。
2. 卡片明确显示“自费可选/需提前预约”，费用不含中存在对应项目。
3. 模型返回的路线、车程、活动强度和 `spots` 能在编辑器和最终数据中看到。
4. 所有现有图片、换图、进度、保存和导出测试继续通过。

## 五、第二批：修复每日文案和每日图片故事

### 5.1 客户文案模型使用专用提示词

把当前写在 `app/server/app.mjs` 的长字符串迁移为 `app/prompts/customer-itinerary-editor.md`，并写入以下核心规则：

- 先制造向往，再说明稀缺价值，再说明具体安排，最后专业兜底；
- 每日正文按已有事实形成时间推进；
- 必须说明客户会做什么或看到什么、为什么值得、奢游如何安排、它在路线中的意义；
- 信息不足时宁可简洁，不虚构具体时刻、动物出现、设施或已包含项目；
- 自费/可选体验可以成为当天高潮，但状态和费用边界必须同时写清；
- 相邻日期不能只是换词重复；
- 不复制供应商口吻、景点百科和内部说明。

提示词使用版本号，例如 `CUSTOMER_COPY_PROMPT_VERSION`，生成任务记录所用版本，后续才能追溯。

### 5.2 增加每日文案质量闸门

`app/server/content-quality.mjs` 逐日检查：

- 是否只剩“前往—游览—入住”的流水账；
- 是否有客户动作、现场画面或体验价值；
- 是否把同一句话重复用于多天；
- 是否出现无依据保证；
- 自费/可选/待确认状态是否明确；
- 正文与费用包含/不含是否冲突；
- 是否出现供应商、成本、内部报价等客户禁用词。

不要只用字数判断好坏。质量不合格时，只把对应 DAY 的原始事实、问题清单和前后一天摘要交给模型重写一次，不重新生成整份行程和全部图片。

### 5.3 按图片故事生成每日图片位

每日图片数量不按文案字数决定，也不固定塞满四张。建议规则：

- 纯抵达、转场、返程日：目标 1—2 张；
- 普通核心体验日：默认目标 2 张；
- 有多个确认或可选卖点且画面差异明确：目标 3—4 张；
- 最终仍以合格图片数量为准，可以少于目标数量。

每个图片位必须有独立角色，例如：

- `environment`：地点与环境；
- `action`：客户参与方式；
- `detail`：服务、文化或体验细节；
- `transition`：草原飞机、船只等有价值的转场；
- `closing`：返程或情绪收束。

不要用四张相似动物照片完成四个位置。

### 5.4 调整图片位结构

`app/src/lib/imageSlots.js` 不再依赖当前几乎不会出现的 `spot.composite` 才创建第二张图。应由经过校验的 `spot.imageRoles` 或每日图片故事明确建立固定 `slotId`：

```text
day:{dayId}:spot:{spotId}:environment
day:{dayId}:spot:{spotId}:action
```

图片蓝图只能规划这些已经存在的固定位置，不允许模型临时发明位置。

### 5.5 图片搜索仍遵守严格边界

- 搜索输入必须包含当天完整正文、路线、节奏、餐食、酒店、所有 `spots` 和状态。
- 自费体验可以是高优先级图片，但相邻客户文案状态必须正确。
- 继续执行真实下载、本地保存、视觉终审、全局去重和用户锁定保护。
- 搜不到合格图时留空，不允许用错误地点或廉价图片填满。

### 第二批验收

使用同一份坦桑尼亚真实文件验证：

1. DAY 1—DAY 7 文案有各自清楚的体验重点，不再同义重复。
2. DAY 3/4/5/6 的自费卖点可以成为主图，并正确显示状态。
3. 普通游猎日不再只产生一个笼统的“塞伦盖蒂西部游猎”图片位。
4. 每日图片角色不同，不重复使用同一文件、同一来源图或相同画面。
5. 严格终审失败仍然留空，不降低门槛。

## 六、第三批：补齐资料覆盖、冲突检查和最终成品审查

### 6.1 原始资料覆盖台账

导入时为原始表格内容建立内部台账，每条信息记录：

- 来源工作表和位置；
- 原始文字；
- 分类：基础信息、每日、酒店、交通、餐食、费用、提醒、内部信息；
- 去向：客户展示、内部保留、重复合并、明确舍弃；
- 对应目标字段或舍弃原因。

确认页只显示简洁的遗漏和冲突摘要，完整台账保存在项目内部，不增加用户操作负担。

### 6.2 扩展生成前冲突检查

在现有日期检查基础上增加：

- 每日编号和总天数；
- 酒店入住晚数合计与每日住宿；
- 酒店中文名、英文名、房型、餐食和确认状态缺失；
- 路线节点、交通方式、移动时间和住宿地点是否矛盾；
- 车辆等级、座位数和车型承诺；
- 正文、费用包含、费用不含和体验状态是否冲突；
- 返程日住宿类型；
- 时效信息是否缺少来源或复核日期。

会影响费用或履约的冲突必须在确认页阻止生成；普通资料缺失可以标为待确认后继续。

### 6.3 费用跨板块同步

建立统一检查：

- `included` 体验不能同时出现在 `excluded`；
- `optional_paid` 必须进入 `excluded`；
- `pending` 进入待确认信息；
- 用户在编辑器把体验改为已购买时，同步更新费用边界；
- 删除体验时提示是否同步删除对应费用项。

### 6.4 扩大 2000px 最终复查

保留现有图片复查，再增加：

- 标题是否遮挡、溢出或换行异常；
- 每日文案是否明显重复、残缺或暴露供应商语言；
- 自费/可选/待确认状态是否显示；
- 状态与费用包含/不含是否冲突；
- 必需板块和固定页尾是否存在；
- 图片与文字是否对应；
- 是否有破图、异常大空白、卡片被截断或下半部分缺失。

发现图片问题时只重搜目标位置；发现文案问题时只重写目标板块；发现事实或费用冲突时不得自动修改，应返回编辑器并明确提示。

### 第三批验收

1. 原始文件每条非空信息均能在覆盖台账找到去向。
2. 构造酒店晚数冲突、费用冲突、车型承诺冲突时能够被阻止。
3. 真实 2000px 成品没有标题遮挡、下半部分缺失、破图、内部审核用语和异常大空白。
4. 最终复查异常不会静默进入正式版本。

## 七、自动化测试清单

### 内容与事实

- 模型每日结构按 `index` 正确合并；
- 缺字段保留原事实，重复/缺失 index 拒绝；
- 每日文案重复、流水账、内部禁用词能够被识别；
- 自费体验可以成为主卖点和主图；
- 自费、已含、待确认状态与费用边界一致；
- 酒店晚数、路线交通、日期和返程住宿冲突检查。

### 图片

- 普通体验日能够建立两个不同角色的图片位；
- 转场日允许一个位置，丰富日允许三至四个位置；
- 蓝图不能发明 `slotId`；
- 自费主图不再被状态直接拒绝；
- 终审、全局去重、锁定、跨模块移动、上传和单槽重搜保持通过；
- 缺图不会显示破图或内部审核文案。

### 成品

- 2000px 导出完整；
- 标题、页尾、长页下半部分、费用状态和每日图片卡完整；
- 客户成品不含审核分数、来源、内部字段和供应商信息。

## 八、真实回归要求

不能只用静态样例或旧项目。每一批完成后都使用全新项目、全新浏览器数据和真实供应商 Excel：

1. 保存输入文件名、任务 ID、蓝图 ID、图片账本 runId 和正式导出文件。
2. 截图确认页、生成进度、DAY 1—DAY 7、费用不含、自费状态、图片换图弹窗和最终页尾。
3. 列出每天的 `spots`、状态、图片角色、候选数、采用数和留空数。
4. 对照原始文件确认没有改动日期、人数、路线、酒店晚数、餐食和费用事实。
5. 执行窗口只提交“待复核”，不得自行关闭 `AUD-014/015/016`。

## 九、推荐执行顺序与交付方式

推荐严格按三批执行：

1. 第一批：状态、模型输入、结构合并和旧规则冲突。
2. 第二批：每日文案质量和多图故事。
3. 第三批：覆盖台账、完整冲突检查和最终成品复查。

每批都先通过自动化和真实回归，再进入下一批。不要同时大改 UI、图片审核和数据存储；本轮核心是把现有规范真正接入当前流程，而不是重做整个工具。

执行窗口交付时必须提供：修改文件、关键逻辑、自动化结果、真实任务证据、截图路径、仍存在的边界，以及对现有功能的回归结果。
