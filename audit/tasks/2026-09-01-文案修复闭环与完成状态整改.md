## 第一部分：用户可读执行说明

### 1. 本次真正要解决的问题

分级推理与图片超时整改后，完整流程中位数已经从 `24分55秒` 降至 `11分54秒`，但三次真实回归仍分别残留 `15 / 9 / 21` 项文案问题。

真实问题不是品牌审查没有运行，而是：

1. 高推理品牌审查能够准确发现 DAY 文案、注意事项及其他模块的问题；
2. 后续低推理局部改写一次接收过多问题，又没有收到对应品牌规则的完整执行要求，连续两轮仍可能修不好；
3. 注意事项等错误结构没有被程序拒绝，最后被前端拼成一个大段落；
4. 程序把“所有流程阶段已经运行”误当成“内容质量已经通过”，仍显示100%并进入普通编辑器；
5. 编辑器只展示少量问题，用户看不到系统已经发现的完整问题清单。

本次目标是建立真实闭环：

```text
发现问题
→ 判断问题类型
→ 注入对应正式品牌规则和必要上下文
→ 使用合适推理档位进行小范围修复
→ 使用同一规则检查修复结果
→ 未修好则有限升级或明确待修订
→ 全部通过后才显示100%并进入普通编辑器
```

### 2. 已确认采用的产品方案

#### 2.1 规则必须真正进入局部修复调用

- 高推理能力不能代替品牌规范；模型只有收到明确规则，才知道奢游要求怎样表达。
- `rules/03-品牌文案与模块内容.md` 继续是唯一正式品牌标准。
- 程序按 COPY 编号维护“运行时规则卡”。规则卡只是正式规则的程序执行投影，不得成为另一套独立标准。
- 每张规则卡至少包含：规则编号、规则版本、适用字段、必须做到、禁止表达、事实依据要求、合格判断和失败处理。
- 局部修复只注入本次问题相关的规则卡，不把01—06全文塞给模型，也不能只给“不要流水账”“要有价值”等模糊概括。
- 正式规则、运行时规则卡、提示词调用和生成后检查必须通过规则落实对照表和自动测试保持一致。

#### 2.2 按问题难度分配修复方式

**程序直接处理或阻止，不调用模型：**

- 注意事项、费用、DAY、酒店等字段的数据结构；
- 标题天数晚数格式；
- 费用项目数量与源数据一致性；
- 空字段、非法数组、非法对象；
- 测试姓名、内部信息和客户不可见字段；
- 确定性事实、安全和履约冲突。

**低推理小补丁：**

- 普通语气润色；
- 简单重复词和句式调整；
- 不涉及前后逻辑的单字段精简；
- 单条注意事项措辞；
- 简单格式和客户表达调整。

**直接使用小范围高推理：**

- `day_no_value`：DAY 缺少独立旅行价值；
- `day_no_progression`：DAY 与前后日期缺少推进关系；
- `day_near_duplicate`：相邻或多个 DAY 高度同义；
- 当天事实有限，需要在不虚构的前提下形成具体画面；
- 路线亮点、酒店或体验需要结合整程主线形成独特价值；
- 其他明确依赖跨字段、跨DAY或整程判断的问题。

不得先让低推理对明确复杂的语义问题连续失败两次，再无条件放行。

#### 2.3 小范围任务，不再一次改几十个字段

- 每个补丁任务只处理一个 DAY、一个酒店或一个明确模块中的少量相关字段。
- DAY 高推理补丁只提供：当前 DAY、前后 DAY 摘要、当天原始事实、整程主线中的 DAY 角色、对应 COPY 规则卡、当前不合格文案和允许修改路径。
- 不把整份行程和所有问题交给一个所谓“局部补丁”。
- 修复任务共用现有模型总并发控制，初始总并发保持2；不得为了追回时间无限增加并发。
- 每个目标最多一次低推理修复和一次高推理升级；明确复杂问题可以直接进入高推理，不浪费一次低推理。
- 到达上限仍未通过时停止自动重试，进入“待修订”，不得整份重写。

#### 2.4 修复后的检查闭环

- 首次高推理品牌审查负责完整发现问题。
- 程序按问题类型分流，并只允许修改命中路径。
- 每个补丁应用后，立即使用对应确定性检查和规则卡验收目标字段。
- 简单低推理补丁未通过时，只升级目标字段到高推理一次。
- 复杂语义补丁完成后，只复核修改字段及必要上下文；不重新审查没有变化的整份文案。
- 未授权路径、错误结构、事实改变、费用变化、内部信息或证据不足的补丁必须拒绝并保留安全原值。

### 3. 注意事项结构必须由程序保证

正式注意事项结构必须明确为：

```json
[
  {
    "title": "分类标题",
    "items": ["提醒一", "提醒二"],
    "tone": "gold"
  }
]
```

要求：

- 模块 `expectedShape.notes` 必须声明元素结构，不能只写空数组。
- 当前生成结果中的字符串数组不得作为合法结构进入合并与渲染。
- 合并器不得对字符串执行对象展开。
- 生成后检查必须明确产生“注意事项结构非法”，不能只报告覆盖类别不足。
- 前端必须逐条渲染 `items`，禁止使用空格把多个条目拼成一个段落。
- 旧项目历史字符串数组允许兼容读取，但必须转换为明确的兼容结构并标记待复核，不能作为新生成通过证据。

### 4. 完成状态和用户界面

页面必须区分以下状态：

| 情况 | 页面状态 | 100% | 普通编辑器/导出 |
|---|---|---:|---|
| 文案、事实、图片、排版和2000px检查全部通过 | 生成完成 | 显示 | 允许进入普通编辑器，允许后续正式导出 |
| 自动流程结束，但仍有普通表达问题 | 待文案修订：N项 | 不显示 | 不自动进入普通编辑器；可以继续自动修复或由用户明确进入“修订模式” |
| 事实、费用、安全、内部信息或结构错误 | 已阻止生成 | 不显示 | 禁止进入普通编辑器和正式导出 |
| 接口、网络或程序异常 | 生成失败 | 不显示 | 显示真实原因和目标重试入口 |

要求：

- 不使用假的 `99%` 冒充状态；未通过时以明确状态文字替代完成百分比。
- “待文案修订”不是“生成失败”，前面已经完成的图片和版面结果不得作废。
- “修订模式”必须有持续可见的待处理标识，不能伪装成正常完成状态。
- 修订模式下不得正式导出；用户或模型修改后必须重新运行相关规则检查，全部通过后才能转为“生成完成”。
- 所有已知问题必须按模块、DAY、规则编号完整展示，不能只显示前两条。
- 事实、费用、安全、内部信息、履约和数据结构问题必须阻止；不得通过文案润色绕过。
- 普通表达问题在有限自动修复后仍存在时进入“待文案修订”，不能显示100%。

### 5. 不允许改变的内容

- 不修改模型名称、API Key、接口地址、计费配置或 `.env`。
- 不修改图片搜索、图片视觉审核、图片并发和超时整改结果，除非本任务回归证明存在直接冲突并先提交产品决策。
- 不恢复整份文案重写。
- 不把01—06全文无差别塞进每次模型调用。
- 不建立第二份独立品牌标准。
- 不降低日期、人数、路线、酒店、晚数、交通、餐食、费用、体验状态和履约状态保护。
- 不把未通过的2000px预览称为最终客户成品。
- 不修改冻结旧项目。

### 8. 验收标准

#### 规则进入运行链路

- 每个局部补丁证据能看到实际注入的 COPY 规则编号和规则版本，但不得记录模型推理正文或敏感完整请求。
- DAY 价值、推进和重复问题实际进入高推理小补丁，而不是固定低推理。
- 简单问题保持低推理；结构和事实问题由程序处理或阻止。
- 每个目标任务范围可追溯，不出现一次补丁修改几十个无关字段。

#### 注意事项

- 新生成的 `notes` 只能是合法分组对象数组。
- 字符串数组、对象字段缺失和 `items` 非数组必须被拒绝或阻止完成。
- 最终页面按分类和条目展示，不能拼成一整段。

#### 完成门禁

- `contentQuality.passed=true`、事实安全通过、图片流程结束、图文一致性通过、真实2000px QA通过后，才显示100%并进入普通编辑器。
- 普通文案仍有问题时显示“待文案修订：N项”，不自动进入普通编辑器，不允许正式导出。
- 事实、费用、安全、内部信息、履约和结构问题显示“已阻止生成”。
- 系统异常显示“生成失败”，不能与质量问题混用。
- 所有已知问题完整展示，数量与后台一致。
- 明确进入修订模式时保持醒目标识；修订后必须复检才能转为完成。

#### 已知真实样本回归

- 使用 `formal-2-2026-08-31T11-20-43-874Z` 同源工作簿建立全新项目验证。

- 标题、亮点、酒店、交通、费用、定制师和时效信息同类问题也必须覆盖，不能只修用户截图。
