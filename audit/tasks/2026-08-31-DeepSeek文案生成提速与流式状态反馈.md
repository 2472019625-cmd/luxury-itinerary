## 第一部分：用户可读执行说明

### 1. 本次真正要解决的问题

当前问题不是只有“页面没有动画”，而是两类问题同时存在：

1. **真实生成时间过长**：DeepSeek 一次生成整份长文案，之后整份内容至少再进入一次品牌复核，图片蓝图还要等待文案链路结束；大任务基本串行。
2. **等待过程不可判断**：单次 DeepSeek 请求使用非流式方式，数分钟内页面只能停留在固定阶段，用户无法判断模型是在推理、输出、解析、重试还是已经异常。

本次目标是：

- 页面持续显示真实工作状态，不再像卡死；
- 把整份文案拆成可并行、可单独重试和可保存的模块；
- 每份成品仍必须完成一次独立品牌审查；审查没有发现问题时不再调用改写，发现问题时只改目标字段、酒店或 DAY，不得整份重写；
- 某一天或某个模块失败时，只处理失败部分；
- 图片规划仍从整份行程的内容与视觉主线出发，不能退化为按原始表格机械搜图；
- 文案、图片、排版和最终检查全部结束后，才允许进入编辑器。

### 2. 当前真实问题

当前文案链路大致为：

```text
整份客户文案首稿
→ 最多两轮整份品牌复核
→ 图片蓝图
→ 图片搜索和审核
→ 最终版面检查
→ 编辑器
```

当前 DeepSeek 单次请求在空内容或非法 JSON 时最多进行三次完整尝试。单次请求期间，前端虽然定时读取任务状态和耗时，但无法显示模型是否已经返回数据，也无法显示当前正在推理、输出正文或重试。

当前图片蓝图主要使用原始行程事实。它不能在提速改造中被进一步简化成“按地点或游猎关键词直接搜图”，否则连续多天游猎会出现大量重复动物、草原和车辆图片。

#### 2.1 第一、二批实施后的真实新问题

2026-08-31 坦桑尼亚 7 日全新项目真实回归总耗时为 `24分55秒`。完整时间线：

`audit/evidence/2026-08-31-DeepSeek文案流式并发整改/real-run-2026-08-31T07-48-43-676Z/02-generation-timeline.json`

关键路径为：

```text
0:00—1:25   整程内容与视觉主线
1:25—8:50   图片蓝图（与分模块文案和品牌审查并行）
8:50—24:34  图片搜索、下载、视觉审核和重试
24:34—24:55 最终 2000px 版面检查
```

本次文案在 `8:02` 已完成，图片蓝图在 `8:50` 才完成，因此普通文案和品牌审查不是本次最终完成时间的主要瓶颈。图片阶段实际占约 `15分44秒`，是最大瓶颈。

真实图片结果：21 个图片位、41 次搜索、146 张候选、15 张完成视觉审核、4 张自动采用、17 个失败图片位；其中 14 个失败原因为“图片槽位处理超时”。这证明当前主要问题不是单纯“没有搜到图”，而是视觉审核超时被当成图片失败，并触发了后续重复搜索。

当前图片槽位以累计 `90秒` 同时覆盖搜索、来源页提取、下载、初审、终审和后续轮次；前序步骤消耗时间后，视觉审核可用时间不足。终审异常分支还会把候选标记为 `hard_rejected`，没有区分图片明确不合格与审核服务超时。

本次已记录 DeepSeek 总 Token 至少为 150,970，其中已报告推理 Token 67,376；空内容后成功重试的尝试用量可能另有累计。图片蓝图单独使用 33,855 Token，其中推理 Token 14,212，实际耗时 7分25秒。

### 3. 本次采用的总体方案

本任务分三批实施，但使用同一份任务书，避免一次改动过大。第一、二批先行实施；第三批基于上述 24分55秒真实回归新增，随后已由用户正式确认并完成实施，结果见本文末尾与第三批证据目录。

#### 第一批：先解决卡死感和无效等待

- DeepSeek 改为服务端流式接收。
- 前端显示真实阶段、当前任务、是否已收到模型响应、重试次数、完成数量和累计耗时。
- 不向用户展示 DeepSeek 的具体推理内容。
- 不向用户展示未完成、未校验的文案。
- 每份成品必须进行一次独立品牌审查；审查本身不能省略，但没有发现问题时跳过改写调用，发现问题时只启动目标字段、酒店或 DAY 的局部改写。
- 空内容、非法 JSON、超时和限流必须显示真实状态，不能静默重新等待。

第一批主要改善可感知状态，并减少“审查没有发现问题却仍进入改写”的浪费；不能虚假宣称流式本身会大幅缩短最终完成时间。

#### 第二批：真正缩短文案完成时间

在确定性事实确认后，先生成并检查一份短小的“整程内容与视觉主线”。它不是完整文案，只负责确定：

- 整趟旅行的核心价值和叙事节奏；
- 每天在整份行程中的内容角色；
- 每天与前后日期的差异；
- 酒店、交通、餐饮、费用和每日行程的表达重点；
- 每天的视觉重点和需要避免的重复主题。

随后并行处理：

```text
确定性事实
→ 生成并检查整程内容与视觉主线
   ├─ 全局文案：标题、副标题、概览、亮点
   ├─ 酒店与交通文案
   ├─ 每日行程文案：按天有限并行
   ├─ 费用、提醒和收尾文案
   └─ 整程图片蓝图与后续图片搜索
→ 各模块检查与局部修复
→ 统一组装和跨模块一致性检查
→ 图片、排版及 2000px 检查
→ 全部完成后进入编辑器
```

图片蓝图与文案可以并行，但二者必须共享同一份“整程内容与视觉主线”。图片蓝图不得只依赖原始表格中的地点和简单活动词。

候选图片的搜索和下载可以在文案生成、独立品牌审查期间并行进行，但最终自动采用和放置必须等待客户文案首稿及独立品牌审查结束，并执行一次“最终文案—图片一致性检查”。只有通过一致性检查的图片位才可以自动入稿。

文案与图片采用局部联动：

- 普通语气润色、句式调整和不改变主题的精简，不触发重新搜图；
- 文案主题发生改变时，只重新检查相关图片位；
- 用户确认或确定性数据更新导致事实、体验状态发生变化，或者图片与最终文案不一致时，只重新检查或搜索目标图片位；模型擅自删除或改变事实时必须拒绝补丁并恢复原始事实，不能用重搜图片代替事实保护；
- 不得因为一个 DAY 或一个酒店文案变化，重新规划或搜索整份行程的所有图片。

#### 第三批：分级推理与图片超时整改（已确认执行）

第三批不是继续扩大文案并发，而是处理真实关键路径：图片蓝图过度推理、视觉审核串行、审核超时误判和重复搜索。

推理强度调整为：

| 任务 | 最终建议 |
|---|---|
| 整程内容与视觉主线 | 高推理 |
| 分模块文案首稿、每日行程、酒店/交通/餐饮 | 低推理 |
| 图片蓝图落位与搜索词 | 低推理 |
| 每份成品独立品牌审查 | 高推理 |
| 品牌审查后的目标补丁 | 低推理 |
| 费用格式化、JSON修复、空内容重试 | 关闭思考 |

整程内容与视觉主线继续承担复杂的全局内容和视觉决策。图片蓝图必须读取该主线，但只把已经确定的视觉角色落实为真实 `slotId`、搜索主体、`mustHave/prefer/forbid`、查询词和证据引用，不得重新输出整份分析。降低图片蓝图推理不能退化为按地点或“游猎”关键词机械搜图。

图片处理改为连续流水线：

```text
图片位 A：搜索 → 下载 → 初审 → 单图终审 → 自动采用/人工候选/明确失败
图片位 B：搜索 → 下载 → 等待视觉审核
图片位 C：正在搜索
```

搜索下载槽位并发保持 3；视觉审核建立独立队列，初始并发为 2，稳定后最高为 3。不得直接把视觉审核并发提高到 5 或更高。

每个图片位第一轮结束后按以下规则停止或继续：

- 有自动通过图：立即停止该图片位；
- 没有自动通过图，但已有通过基础技术与安全检查、没有明确硬错误的人工候选：保留候选并停止自动重搜；
- 只有全部候选明确硬拒绝，或没有任何可下载候选时，才执行第二轮搜索；
- 视觉审核超时或服务异常：保留候选为 `manual_review`，不得标成 `hard_rejected`，不得为追求自动通过继续重搜；
- 第二轮仍无结果：留空完成，在编辑器支持目标位置“搜索更多”或上传；
- 取消高优先级图片位第三轮自动搜索。

终审策略改为每个图片位先终审排序第一的 1 张；只有它被明确硬拒绝时才终审第 2 张。未终审候选可以保留预览，但采用资格必须符合 04 正式规则。

只有水印、破图/严重低质、主体完全错误、明确地点或品牌错误、命中 `forbid` 等有事实证据的情况可以硬拒绝。超时、429、5xx、非法返回和审核服务不可用属于系统异常，不是图片质量结论。

### 4. 前端应该展示什么

生成页至少显示：

- 当前阶段；
- DeepSeek 是否已经开始响应；
- 当前正在处理的模块或 DAY；
- 文案模块完成数，例如 `7/12`；
- 图片蓝图、图片搜索和版面检查状态；
- 当前是否重试以及第几次尝试；
- 已用时间；
- 最终缺图数量。

示例：

```text
正在生成客户文案
DeepSeek 已响应，正在生成正文
每日行程：DAY 1、2、3 已完成，DAY 4 生成中
酒店文案：2/3 完成
图片蓝图：已完成
图片搜索：8/24 个位置完成
DAY 5 返回格式不完整，正在第 2 次尝试
已用时：1分36秒
```

前端不得展示：

- DeepSeek 的具体思考过程或 `reasoning_content`；
- 未结束的半句文案；
- 未闭合的 JSON；
- 未经过事实和规则检查的草稿；
- 提前进入编辑器的入口。

### 5. 不允许改变的内容

- 本任务书不得自行覆盖 `rules/01—06`。但并行方案会改变 `FLOW-001` 的阶段依赖：用户确认执行后，执行窗口可以同步更新 `rules/01-产品流程与完成状态.md` 及规则落实对照表，使正式流程与真实程序一致；02—06 的事实、文案、图片、版式和运行要求不得借本任务改写。
- 不改变“全部生成及实际 2000px 检查结束后才能到 100% 并进入编辑器”。
- 不把流式正文当作最终文案展示或开放编辑。
- 不展示、保存或记录模型具体推理内容。
- 不降低日期、人数、路线、酒店、晚数、交通、餐食、费用和履约状态的确定性保护。
- 不把图片蓝图简化为原始表格关键词搜图。
- 不恢复独立图片审核页。
- 不改变图片搜索、图片视觉审核和最终长图视觉检查的模型路由。
- 不修改或输出 API Key、接口地址、计费配置和任何 `.env` 文件。
- 第三批采用分级推理：整程内容与视觉主线、每份成品独立品牌审查保留高推理；文案模块、图片蓝图和目标补丁使用低推理；机械格式化、JSON 修复和空内容重试关闭思考。不得把降低推理解读为降低事实、品牌或图片规则。
- 不修改冻结旧项目。

### 6. 异常处理规则

- **尚未收到模型响应**：前端显示“正在等待模型响应”和已等待时间，不能伪造生成百分比。
- **已经收到推理流**：只显示“模型已响应，正在分析”，不得显示推理正文。
- **开始收到最终正文**：显示“正在接收结构化结果”，不得提前解析为客户内容。
- **流式中断**：保留已完成模块；只重试当前失败模块。
- **空内容或非法 JSON**：显示失败模块、尝试次数和原因；不得让用户误以为仍在第一次生成。
- **429 限流**：降低新任务并发，按有限退避重试；已经完成的模块不得作废。
- **超时或网络错误**：只处理当前模块，不能自动重跑整份行程。
- **局部文案不合格**：只重写对应字段、酒店或 DAY。
- **普通文案润色**：不触发重新搜索图片；只有用户确认或确定性数据更新导致主题、事实或体验状态变化，或者最终图文不一致时，才重新检查或搜索相关图片位。模型擅自删除或改变事实必须拒绝并恢复原值。
- **确定性事实被改变**：拒绝目标补丁并恢复原始事实；不应因此自动重写其他已通过模块。
- **最终仍失败**：保留安全原文或已完成结果并明确标记待复核；能否完成必须继续服从 01 和 03 的正式门禁。

### 7. 什么结果才算完成

本任务只有同时满足以下条件才算实施完成：

1. DeepSeek 调用真实使用流式返回，服务端能够区分推理流和最终正文流。
2. 前端能持续显示真实状态，长请求期间不再数分钟停在无法解释的固定状态。
3. 只记录是否收到推理流、推理字符数量和最后响应时间；推理正文收到后立即丢弃，不向前端、日志、任务文件、客户数据或证据暴露，也不进入可恢复的内存结果。
4. 每份成品完成一次独立品牌审查；没有问题时不调用改写，发现问题时只改目标字段、酒店或 DAY，不整份重写。
5. 文案已拆为可独立完成和保存的模块；每日行程可以有限并行。
6. 一个 DAY 或模块失败时只重试目标模块，其他已完成结果保持不变。
7. 图片蓝图和文案共享整程内容与视觉主线，连续相似行程具有跨日差异和去重规划。
8. 候选搜索可以与文案并行，但最终自动采用和放置必须等待文案首稿、品牌审查和最终图文一致性检查完成。
9. 自动流程未完成时不能到 100%，不能进入编辑器。
10. 使用相同真实行程记录改造前后耗时、调用次数、Token、费用、失败与重试情况。
11. 自动测试、全新项目真实回归和独立审查完成。

### 8. 实施阶段与范围

#### 阶段 A：DeepSeek 流式接收和真实状态

要求：

- 服务端消费 SSE 数据：最终 `content` 可以累计到本次调用的临时结果；`reasoning_content` 不得累计正文，只增加字符计数、更新“已收到推理流”标记和最后响应时间，然后立即丢弃片段。
- 除接收瞬间完成协议解析所必需的临时变量外，`reasoning_content` 不得进入可恢复内存结果、项目、日志、前端响应或证据。
- `content` 在流结束后统一解析 JSON；解析完成前不得合并到客户数据。
- 服务端任务状态至少增加：`providerResponded`、`streamPhase`、`attempt`、`receivedContentChars`、`completedUnits`、`totalUnits`、`lastEventAt`。
- 前端可以继续轮询本地任务接口，不要求浏览器直接连接 DeepSeek；API Key 只能存在服务端。
- 长阶段的耗时必须持续更新，进度必须单调且来自真实阶段。

#### 阶段 B：保留独立品牌审查，取消无效整份改写

- 每份客户成品必须执行一次独立品牌审查，不能因为程序检查无问题而取消审查。
- 独立品牌审查使用独立调用和专用提示词；一次返回可以同时提供问题清单及对应字段补丁，没有发现问题时补丁为空并直接通过。
- 品牌审查发现问题时只允许返回目标字段、酒店或 DAY 的补丁；只有补丁无效、应用后仍不合格时，才单独调用目标范围的局部改写，不得重新生成整份内容。
- 整份一致性审查可以读取完整成品，但修改动作必须拆成目标补丁；不得要求模型重新返回和覆盖整份文案。
- 事实字段不交由模型选择或改写。

#### 阶段 D：第三批图片超时、调度与推理整改

1. **分级推理落地**

2. **图片超时语义修复**
   - 终审 `AbortError`、超时、429、5xx、网络错误和非法 JSON 不得进入硬拒绝分支；
   - 候选通过下载、解码、尺寸、来源安全和基础技术检查，且没有明确硬错误时，审核异常后保存为 `manual_review`、`adoptable=true`、`requiresDecision=true`，理由明确为“视觉审核未完成，需人工确认”；
   - 未完成视觉终审的候选不得自动采用；用户人工采用时继续留下决定和来源记录；
   - 只有模型或确定性检查提供明确硬错误码时才允许 `hard_rejected`。

3. **超时预算拆分**
   - 不再让搜索、下载、初审、终审和所有轮次无区分地共享一个不可解释的剩余时间；
   - 分别记录搜索下载、初审、终审的开始、结束、耗时和超时阶段；
   - 保留单图片位总体预算，避免无限运行，但审核异常必须按人工候选降级，不能靠延长总体超时掩盖问题；
   - 具体阶段秒数由真实压测决定并集中配置，不散落在业务代码中。

4. **连续流水线与独立审核队列**
   - 单个图片位完成搜索下载后即可进入审核，不等待同优先级所有图片位搜索完成；
   - 搜索下载并发保持 3；视觉审核使用独立队列，初始并发 2、最高 3；
   - 初审拼版与单图终审的模型调用必须计数和计时；
   - 每个槽位优先终审第 1 张，只有明确硬拒绝才终审第 2 张。

5. **停止重搜条件**
   - 自动通过、用户锁定、存在可人工采用候选、明确留空或预算内无结果，均可形成图片位终态；
   - 视觉审核超时后存在人工候选时停止自动重搜；
   - 只有没有可下载候选或候选全部明确硬拒绝时才进入第 2 轮；
   - 自动搜索最多 2 轮，不恢复高优先级第 3 轮；
   - 编辑器“搜索更多”继续只影响目标 `slotId`。

6. **状态与统计统一**
   - `hardRejected` 只统计明确硬错误；
   - 单独统计 `auditTimeout`、`auditUnavailable`、`manualReviewCandidates`、`manualReviewSlots`、`emptySlots`；
   - `failedSlots` 不得把拥有可人工采用候选的图片位混同为“没有图片”；
   - 品牌审查完成数、人工候选数量在任务状态、运行总结和最终项目中使用同一口径。
