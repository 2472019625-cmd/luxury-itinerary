## 一、任务定位

本任务只精简 Planner 的视觉规划输出，并把图片位编号、必需性、可移除性、版面位置、比例和完整来源绑定等确定性字段交给程序生成。

本任务不重新设计知识库、Preview-First、Step4、视觉审核或 Renderer。任务书只用于执行约束和验收，不得替代 `rules/01—06` 成为新的规则来源。

已按本次授权同步 `rules/03` v1.17 与 `rules/04` v2.3 的精简契约和输入兼容边界；业务规则不变。实现前仍须保存当前基线，确认 Copy 既有语义不会被削弱。旧 DAY 主要视觉字段本轮保留；不以模型输出缩短20%作为硬门槛。

必须同时达到三个目标（下游兼容优先于长度）：

1. Planner JSON 明显缩短，减少长 JSON 截断、语法错误和技术补救概率。
2. Adapter 交给 Copy、Image、知识库、Step4 和 Renderer 的标准图片位结构与现有下游契约保持兼容。
3. Planner 已确认的完整画面和合格 Query 从 Planner 到知识库请求保持单一语义来源，不被 Adapter、Query Builder 或不同 Scope 再次理解、换主体或改写。

只做到“JSON 变短”但破坏下游，或只保持下游但没有消除重复字段，均不算完成。

## 二、已确认产品决定

### 1. Parser 与候选图片位置

- Parser 只负责把 Excel 内容整理为结构化事实，不负责建立最终图片位。
- 程序依据解析结果和正式产品规则建立“候选图片位置”。
- 封面、酒店、DAY、餐饮、交通等候选位置可以在 Planner 前确定，但最终是否保留必须结合模块显示规则、图片位必要性和 Planner 的视觉选择。
- 封面主图、每个实际展示酒店主图、每个实际展示 DAY 主图属于程序确定的最低必需视觉覆盖，Planner 无权取消或降级。
- 餐饮、交通和 DAY 辅助图属于条件位或可选增量，不得因为建立了候选位置就强制进入最终版面。

### 2. Planner 调用与职责

- 每份行程只允许一次 Planner 业务规划。
- Planner 在同一次规划中同时决定文案方向和视觉图片规划。
- Planner 必须决定每个最终视觉计划“完整拍什么、为什么拍、主体、动作、必要身份、地点、地点作用和 2—4 条 Query”。
- Planner 不输出最终客户文案，不执行图片搜索，不访问知识库。
- Planner 局部输出问题不得触发整份重新规划。
- 第一次完全没有形成可用 JSON 时，允许一次关闭深度思考的底层技术补救；这不属于第二次业务规划。除此之外不得再次调用 Planner。

### 3. 为什么选择图片

- 每个视觉计划必须保留唯一解释字段 `selectionReason`，说明为什么在现有真实内容中选择这张图。
- `selectionReason` 只用于复盘、校验和 Step4 解释，不得进入 Query 或 Scope。
- 不再同时保留语义重复的 `visualDuty`、`visualGoal`、`differentiation` 和其他同义解释字段作为 Planner 输出。
- `selectionReason` 必须是一句简短、具体、可核对的业务理由，不写“证明当天、补充体验、区别其他图片”等机械说明。

### 4. DAY 内容角色与图片规划

- `dayRoles` 只负责当天在整趟旅行中的作用、与相邻 DAY 的区别和文案处理方向。
- 目标状态是 Planner 不再重复输出两份主要视觉，而不是让 Copy 失去原来依赖的主要视觉信息。
- 删除 Planner 输出中的 `dayRoles.primaryVisualSubject` 前，必须先验证它与新版 DAY 主图 `visual` 在真实输出中的含义是否一致，不能仅凭字段名称推定等价。
- 如果两者等价，Planner 只在 DAY 主图 `visual` 写一次；程序将这一句话原样投影给图片流程和原本确实需要该信息的 Copy 任务。该投影不属于第二次规划，也不新增模型调用。
- 如果两者不等价，暂时保留旧字段并单独报告差异、影响和可选方案；不得为了减少几行 JSON 强行合并或改变 Copy 的选题重点。
- 图片规划是“具体放什么图、为什么放、搜什么词”的唯一权威来源。
- 已证明等价并获准合并后才取消重复维护；本轮保留旧 DAY 主要视觉字段用于兼容。
- DAY 主题、DAY 正文按原有需要接收当天主要视觉。每张图片卡及对应体验文案必须接收自己绑定图片位的 `visual`，包括辅助图；不能全部使用当天主图。不得因精简删除 Copy 既有必要输入，不将 Query 或整份视觉计划作为文案事实。
- 程序只向原本确实消费该语义的 Copy 任务兼容分发，不把全部视觉计划扩散到所有文案任务。Image Skill 读取视觉计划。两者在 Planner 完成后继续并行执行，图片不等待文案成稿。

### 5. 程序负责的确定性字段

程序根据候选位置、模块规则、Planner 结果和模板结构补齐：

- 稳定 `slotId`；
- 下游标准 `role`；
- `moduleType`；
- `required`；
- `removable`；
- `visualTier`；
- 实际 `fieldPath` 与写回位置；
- 图片比例 `aspectRatio`；
- `copyTargetId`；
- 完整 `sourceRefs/sourceEvidence`；
- 用户锁图关联；
- 下游需要的标准图片位字段。

程序不得重新决定 Planner 已确定的完整画面、主体、关键动作和 Query。

### 6. 删除 DAY 主要视觉前的强制依赖审查

删除 `dayRoles.primaryVisualSubject` 不是本任务可以直接执行的机械删字段操作。执行前必须沿真实运行路径确认 Copy Skill、图片适配、写回、Step4 和旧项目读取是否消费该字段。

当前只读审查已经确认存在真实 Copy 输入依赖，因此删除动作处于阻断状态：

- `normalizedDayRoles` 当前通过对象展开保留 `primaryVisualSubject`；
- DAY 主题任务把完整 `dayRole` 放入 `relevantContext.dayRole`；
- DAY 正文任务同样把完整 `dayRole` 放入 `relevantContext.dayRole`；
- `runCopyWriterSkill` 会把完整 Copy task 序列化后发送给 Copy 模型；
- Copy Skill 明确要求依据 `dayRole`、相邻日差异和当天真实体验选择主记忆点，因此即使代码没有直接读取 `dayRole.primaryVisualSubject`，该字段也已进入模型真实输入并可能影响文案选择；
- 图片适配层还把 `dayRoles.primaryVisualSubject` 作为 DAY 图片计划缺少主体时的语义兜底，并用于匹配当天 Spot。

因此执行窗口必须先停止并提交依赖报告，不得在同一步中直接删除字段。优先验证以下最小兼容方案，而不是默认切断 Copy 的视觉输入：

1. 用真实 Planner 输出逐 DAY 比较旧 `dayRoles.primaryVisualSubject` 与对应新版 DAY 主图 `visual`，记录一致、等价但措辞不同、不一致和缺失四类结果；
2. 若业务含义等价，由程序建立兼容投影：`copyDayRole.primaryVisualSubject = dayPrimaryVisual.visual`，并继续传入现有 DAY 主题和 DAY 正文等确实依赖该信息的 Copy 任务；
3. 图片卡片标题或对应体验文案接收各自绑定图片位的 `visual` 原样映射；不能用当天主图覆盖辅助图或其他体验。未绑定图片位的普通 Spot 保持原有事实输入；
4. Copy 兼容投影只复制同一句话，不生成新内容、不读取 Query、不新增模型调用，也不允许 Adapter 改写画面；
5. 对同一输入保存变更前后的 Copy task payload 和 Copy 输出，并运行定向回归，确认 DAY 主题、正文重点、图片卡片标题、状态边界和相邻日差异没有意外变化；
6. 若无法证明新旧语义等价，立即停止删除，保留旧字段并报告依赖，不顺手修改 Copy 逻辑；
7. 图片适配层必须使用新的 `visual` 作为图片语义来源，缺失时标记 unresolved，不得继续依赖 DAY 角色或 `spots[0]` 猜画面；
8. 只有等价性和 Copy 行为回归均通过并取得用户确认后，才删除 Planner 输出中的 `dayRoles.primaryVisualSubject`。

在依赖解除前，任务书其余关于“删除 `dayRoles.primaryVisualSubject`”的条款都属于目标状态，不构成当前直接删除授权。

### 7. `visual` 是完整画面的唯一权威字段

每个新 `visualPlans[]` 项必须包含简短但完整的 `visual`，明确这一张图最终要拍到的单一画面。例如：`角马群横渡河流`。`subject/action/identity/location` 是这张画面的结构化拆分，不能代替完整画面定义。

字段职责固定为：

- `visual`：这张图完整拍什么，是 Planner 对当前图片位画面的唯一最终决定；
- `subject/action/identity`：用于 Query 安全校验、有限局部修复和视觉审核的结构化锚点；
- `location/locationRole`：只决定 Scope 和地点是否属于画面身份；
- `queries`：Planner 已决定的实际搜索词；
- `selectionReason`：为什么选择这张图，只用于复盘、校验和 Step4 解释。

Adapter 必须把 `visualPlans[].visual` 原样映射为下游 `primaryVisualSubject`。禁止根据 `subject + action + location` 重新拼接、扩写、改写或替换完整画面。`locationRole=scope_only` 时，地点尤其不得被 Adapter 拼回 `visual`、`primaryVisualSubject` 或 Query。

“一个画面”按能否在一张自然、真实照片中同时成立判断，不按主体数量或词语数量机械拆分。向导带游客徒步、旁边出现斑马，象群与雪山、角马与斑马共同渡河等都可以是一个自然共现场景；不能因为向导、游客、动物分别也能搜索，就判为复合画面。只有明确的“A或B”、先后发生且无法同框的动作、地点不同的体验，或需要两张照片才能分别证明的场景，才判定需要拆分或 unresolved。不得新增复杂语义拆分系统，只补确定性防误判测试。

新版视觉计划缺少有效 `visual`、不是一张可以直接拍出的具体画面，或经上述自然共现判断后仍包含两个独立场景时，当前 Slot 标记 `unresolved/needs_user_action`；不得由 Adapter、Query Builder、DAY 角色、`spots[0]` 或其他字段猜测补画面。旧项目只在明确旧版本读取分支中继续使用旧 `primaryVisualSubject`，不得成为新版本的隐式兜底。

### 8. Planner Query 到知识库请求的闭环

当前代码审查已经确认：合格 Planner Query 会被原样接受，普通 Scope 切换不会重新生成 Query。因此本任务不重写 Query 系统，只允许为新版精简字段做最小接线并验证既有正确行为没有变化：

1. 接收新版 `visualPlans[].queries`；
2. 对已经满足 2—4 条、简短、无说明性文字、地点作用正确且无重复的 Planner Query，保持原文和原顺序；
3. 继续沿用现有去重、2—4 条限量和确定性安全检查；
4. Query 不合格时，只用 Planner 已拆好的 `subject + action + identity` 做有限局部修复；
5. 无法可靠修复时只挂起当前 Slot，不换主体、不使用完整 `visual` 或旧 `primaryVisualSubject` 重新生成；
6. 优先复用现有 `querySteps/plannerQueries/fallbackQueries/byScope` 等记录证明 Planner 原词、Guard 判定、局部修复词和最终实际请求词；现有证据足够时不新增生产字段；
7. 对未被当前真实路径执行的旧 Query 函数，只需用调用测试、明确入口或注释证明新格式不可达；不要求顺手删除或重构无关旧代码。

同一图片位先形成一次基础 Query Plan。普通具体地点、地区和国家 Scope 必须复用同一组 Query；Scope Resolver 只决定去哪个知识库目录，不得因进入不同 Scope 重新生成、改写或重排 Query。

唯一允许的 Scope 相关 Query 变化是已经确认的酒店身份安全例外：准确酒店目录不存在、搜索范围扩大到所在地区或国家时，每条 Query 必须补入完整酒店名称，并记录来源为 `scope_identity`，后续继续严格验证酒店身份。该例外不得扩展到普通 DAY、景点、餐饮、交通或封面，也不得改变 Scope 层级、fallback 顺序、知识库接口、`top_k` 或 Preview-First。

文件中若仍存在旧 Query 生成函数，只要新格式真实执行路径仍可能调用，就必须显式隔离并用测试证明不可达；如果当前本就没有调用，则保持未调用状态即可，不为“清理干净”扩大修改范围。

## 三、当前问题

当前 Planner 在一份 JSON 中重复输出大量确定性或同义字段。每个图片位同时包含：

- `slotId/role/label/required/removable`；
- `primaryVisualSubject`；
- `visualDuty/differentiation`；
- `location/locationRole`；
- 含中英文六项的 `queryCore`；
- `fidelityQuery/alternateQueries`；
- `sourceRefs`。

同时，DAY 的主要视觉还在 `dayRoles.primaryVisualSubject` 中重复一次。真实 8 日行程生成 27 个 Planner 图片位时，完整 JSON 约 21k 字符，第一次高思考输出曾在约 18k 字符处形成不完整 JSON，依赖一次关闭思考的技术补救才成功。

原任务书提出的精简 `visualPlans` 只保留 `subject/action/identity/location/queries`，缺少“这张图完整拍什么”的唯一字段。如果照此实施，Adapter 只能再次理解并拼接画面，重新形成第二个视觉决策者。

同时，原任务书虽然限制 Query Builder 不得重新决定画面，却未明确冻结当前已经正确的行为。最新代码审查已确认合格 Planner Query 会被原样接受，普通 Scope 切换不会重新生成 Query；本任务只需要接入新版 `queries` 字段并做不变性回归，不能把“闭环”误解成重新开发搜索系统。

本任务必须同时消除结构重复、补足完整画面语义并闭合 Query 直通路径；不得通过删除视觉语义、来源边界或失败开放能力换取更短输出。

## 四、目标流程

```text
Excel
→ Parser 整理原始资料
→ 程序建立候选图片位置与允许的 sourceKey
→ Planner 只调用一次，同时决定：
   - 文案方向
   - 模块处理方向
   - 每个视觉计划完整拍什么（visual）
   - 为什么选择
   - 主体、动作与必要身份
   - 地点与地点作用
   - 2—4 条 Query
→ 程序将精简视觉计划扩展为现有标准图片位：
   - visual 原样映射为 primaryVisualSubject
   - 图片编号
   - 必需或可选
   - 是否允许删除
   - 写回位置
   - 图片比例
   - 完整来源引用
→ Copy Skill 与 Image Skill 并行执行
→ Query Guard：
   - 合格 Planner Query 原文、原顺序通过
   - 不合格 Query 只用 Planner 结构化字段有限局部修复
→ Scope Resolver：
   - 只解析和切换知识库目录
   - 普通 Scope 切换不重新生成 Query
   - 仅酒店扩大 Scope 时补完整酒店身份
→ 现有知识库 / Preview-First / 视觉审核 / Step4 / Renderer
```

## 五、范围

### 允许修改

- Planner 提示词与输出契约；
- Planner 视觉计划校验；
- Planner 失败开放的局部校验与状态记录；
- 候选图片位置生成器；
- `simple-plan-adapter` 对新旧 Planner 格式的兼容与标准图片位生成；
- `simple-plan-adapter` 中 Copy task 的最小兼容投影及其前后行为对照：保留原有 DAY 角色字段，并在证明等价后把 DAY 主图 `visual` 原样投影为 Copy 原先接收的主要视觉；不得修改 Copy Skill 文案规则；
- Planner 到 Adapter 的内部类型和版本字段；
- Planner Query 到知识库请求之间的 Query Guard、Query Builder 和 Scope 应用调用路径，但仅限把新版 `queries/subject/action/identity` 接入现有入口、保持现有正确行为并增加不变性证据；若当前逻辑已符合要求则不得重写；
- 与本任务直接相关的测试、无知识库 dry-run 脚本和报告字段；
- 正式规则中本次明确确认的精简契约与输入兼容约束，以及落实对照表中的证据和状态；不得改写其他正式业务口径。

- 知识库接口、请求协议、Scope 层级策略、Scope fallback 顺序和 `top_k`；
- Preview-First 候选保留规则；
- 图片下载、视觉审核和候选三态；
- Step4 选图、换图、人工上传和锁图行为；
- Renderer、2000px 版式和正式导出；
- Copy Skill 的文案生成规则；
- 模型、API Key、接口地址、计费配置和 `.env`；
- 当前知识库目录结构；
- 重写当前已经正确执行的 Query Guard/Builder 或普通 Scope Query 复用逻辑；
- 仅为代码清理而删除、重构当前未被真实执行路径调用的旧 Query 函数；
- 肯尼亚或任何目的地专用关键词表；
- 通过新增大模型调用补救结构问题；
- 通过整份 Planner 重规划解决单个 Slot 问题。

## 六、候选图片位置契约

程序应建立一个可复用的纯函数候选生成器，Planner 和 Adapter 必须消费同一结果，禁止两处各自推导而产生编号差异。

建议新增独立模块，例如：

`app/server/planner-image-candidates.mjs`

候选位置至少包括：

| 候选类型 | 候选键示例 | 是否必需 | 是否可移除 | 默认比例 | 事实来源 |
|---|---|---:|---:|---|---|
| 封面主图 | `cover` | 是 | 否 | `5:3` | 整程目的地与核心体验 |
| 酒店主图 | `hotel:1` | 展示时必需 | 否 | `16:9` | `hotels.0` |
| 餐饮图片 | `dining:1` | 否 | 是 | `16:9` | `diningExperiences.0` |
| 交通图片 | `transport:1` | 否 | 是 | `16:9` | `transport.0` |
| DAY 主图 | `day:1:primary` | 是 | 否 | `16:9` | `days.0` 及其允许体验 |
| DAY 辅助容量 | `day:1:supporting` | 否 | 是 | `16:9` | `days.0` 内选定体验 |

要求：

- 候选键在本次 Planner 输入中显式提供，Planner 只能从允许候选中选择。
- DAY 辅助图最多 3 个，加主图后每天最多 4 张。
- Planner 返回多个 supporting 时，程序按返回顺序稳定生成 `supporting:1/2/3`。
- 条件模块隐藏后，对应候选不得进入最终标准图片位。
- 必需候选缺少 Planner 视觉计划时，程序生成同一稳定图片位并标记 `unresolved/needs_user_action`，不得拿第一个 Spot、酒店图或泛化活动静默代替。

## 七、Planner 新输出契约

### 1. 顶层结构

新 Planner 输出保留：

- `summary`；
- `selectedHighlights`；
- `modules`；
- `dayRoles`；
- `contentPlacement`；
- `webVerification`；
- `visualPlans`；
- `confirmations`；
- `adjustments`，固定空数组。

在 Copy 解耦、正式规则同步和删除门禁全部通过后的新版输出禁止：

- `imagePlan.slots` 新格式；
- `dayRoles.primaryVisualSubject`；
- `tasks/copyPlan/taskId/dependsOn/parallelGroup/budgetKey/retryLimit/failurePolicy`；
- 最终客户文案；
- 图片最终编号、写回路径、比例、必需性和可移除性。

### 2. DAY 角色结构

```json
{
  "index": 3,
  "role": "迁徙观察高潮",
  "differenceFromAdjacent": "从草原动物观察进入渡河场景",
  "contentAction": "optimize"
}
```

约束：

- `index` 从 0 开始并与输入 DAY 一一对应；
- 不含主要视觉字段；
- 不含最终 DAY 文案；
- 不通过换词制造不存在的相邻日差异。

### 3. 视觉计划结构

```json
{
  "targetKey": "day:4:primary",
  "sourceKey": "days.3.spots.1",
  "visual": "角马群横渡河流",
  "subject": "角马",
  "action": "渡河",
  "identity": "",
  "location": "马赛马拉",
  "locationRole": "scope_only",
  "selectionReason": "这是当天最具辨识度的迁徙观察画面",
  "queries": [
    "角马渡河",
    "角马横渡河流",
    "wildebeest river crossing"
  ]
}
```

字段职责：

- `targetKey`：引用程序提供的候选位置，不是最终 `slotId`。
- `sourceKey`：引用本次输入中允许的真实事实节点。
- `visual`：这张图完整拍什么，是 Planner 的唯一画面定义；必须是一张具体可拍的单一画面。
- `subject`：真正必须入镜的可见主体。
- `action`：定义画面的关键动作，静态空间可为空。
- `identity`：酒店、餐厅、景点或命名实体身份；没有则为空。
- `location`：Scope 解析使用的地点或实体上下文。
- `locationRole`：只能是 `scope_only` 或 `visual_identity`。
- `selectionReason`：为什么选择该画面，只用于解释与审核。
- `queries`：2—4 条同一画面的简短搜索表达，顺序即实际搜索优先级。

`visual` 与 `selectionReason` 不得混用：前者只回答“画面中看见什么”，后者只回答“为什么选择它”。`visual` 不写“体现、证明、补充、区别、收束”等图片职责，不写“A或B”，也不合并必须依靠两张照片才能分别成立的独立体验。多个主体或动作能够在同一真实瞬间自然共现时仍属于一个画面，不能机械拆分。`locationRole=scope_only` 时，具体地名保留在 `location`，不要求写入 `visual`；只有地标、建筑、入口、标牌或实体身份本身必须入镜时，`visual` 才保留相应身份。

不得恢复 `queryCore.subjectEn/actionEn/identityEn`。如果需要英文搜索表达，由 Planner 直接放入 `queries`；程序不得维护动物、活动或目的地翻译词表。

### 4. Query 约束

- 最少 2 条，最多 4 条；两条准确 Query 已足够。
- 第一条必须保留主体和关键动作。
- 后续 Query 可以放宽非核心细节，但不得换主体或丢动作。
- `scope_only` 时地点和目录身份不得进入 Query。
- `visual_identity` 时只有必须入镜的实体身份可以进入 Query。
- `selectionReason`、DAY 角色、相邻日差异、费用状态和说明性文字永远不得进入 Query。
- 禁止使用 `landscape/activity/experience/view` 等泛词凑数量。
- Planner Query 合格时，Query Guard/Builder 必须保持原文和原顺序；不得重新生成、清洗成另一种表达、同义改写、按 Scope 改写或重新排序。
- Query Guard/Builder 只能去重、限量和进行确定性安全检查；不得重新决定画面。
- Query 不合格时只能使用 Planner 已拆好的 `subject + action + identity` 做有限局部修复；不得重新使用完整长句。
- 无法可靠修复时当前图片位标记 `unresolved/needs_user_action`，整条流程继续。
- 同一基础 Query Plan 在普通具体地点、地区和国家 Scope 中复用。只有酒店精确 Scope 扩大到地区或国家时，允许为身份安全补完整酒店名称，并必须记录为 `scope_identity`，不得伪装成 Planner 原词。

## 八、程序扩展为标准图片位

Adapter 必须把新 `visualPlans` 扩展为下游当前使用的标准图片位，保证知识库及其后的代码不感知 Planner 契约变化。

### 1. 画面语义直通

- `visualPlans[].visual` 必须原样映射为下游 `primaryVisualSubject`；
- Adapter 不得根据 `subject/action/identity/location` 重新拼接完整画面；
- Adapter 不得使用 `dayRoles.primaryVisualSubject`、DAY 主题、`spots[0]`、`selectionReason` 或 Query 补写新版 `primaryVisualSubject`；
- 新版 `visual` 缺失或不合格时当前 Slot 直接标记 `unresolved/needs_user_action`，其他 Slot 继续；
- `subject/action/identity/location/locationRole/queries` 分别按原字段职责映射，不能反向覆盖 `visual`；
- 视觉审核必须以同一个 `primaryVisualSubject=visual` 作为核心画面目标，不得在后段换成 Query 或说明性职责。
- 对 DAY 主图，在已经证明旧 `dayRoles.primaryVisualSubject` 与新版 `visual` 业务含义等价后，Adapter 可以把同一个 `visual` 原样复制到 Copy 的兼容输入字段；该复制不能改写内容，也不能携带 Query、Scope、`selectionReason` 或其他视觉计划。
- 图片卡片标题或 Spot 文案继续读取同一个 `visualSubject/primaryVisualSubject`，不得因 Planner 精简退回泛化标题。
- 若等价性未通过，保留旧 Copy 输入，不执行字段合并；图片侧仍以 `visual` 为唯一画面来源。

### 2. 编号与角色

- `cover` → `image:cover:primary`；
- `hotel:N` → 使用原酒店稳定 ID 生成 `image:hotel:<hotelId>:primary`；
- `dining:N` → 使用原餐饮稳定 ID 生成 `image:dining:<diningId>:primary`；
- `transport:N` → 使用原交通稳定 ID 生成 `image:transport:<transportId>:primary`；
- `day:N:primary` → `image:day:N:primary`；
- 同一 DAY 的 supporting 按 Planner 返回顺序生成 `image:day:N:supporting:1/2/3`。

不得改变已有 Step4、锁图和写回依赖的稳定图片位 ID。

### 3. 必需性与可移除性

- 封面、展示酒店主图、展示 DAY 主图：`required:true/removable:false`；
- 餐饮、交通和 DAY supporting：`required:false/removable:true`；
- Planner 不得覆盖上述值；
- 条件模块隐藏时不建立最终图片位，不得把隐藏模块标成 unresolved。

### 4. 来源绑定

- 固定模块的来源由候选键确定；
- DAY 视觉必须验证 `sourceKey` 属于当前 DAY；
- `sourceKey` 必须指向真实存在的 DAY、Spot、酒店、餐饮或交通事实；
- 程序根据已验证的 `sourceKey` 扩展完整 `sourceRefs/sourceEvidence`；
- 自费、需预约和待确认状态必须随来源一起绑定；
- 无效、越界或跨 DAY 的 `sourceKey` 不得回退到 `spots[0]`，当前位直接 unresolved。

### 5. 解释字段映射

- 新结构只保存 `selectionReason` 作为 Planner 原始选择理由；
- 下游如仍需要 `visualDuty/visualGoal`，只能作为固定模块职责或 `selectionReason` 的兼容解释，不得重新定义画面；
- `primaryVisualSubject` 始终只来自 `visual`，`visualDuty/visualGoal` 不得覆盖它，也不得进入 Query；
- 如下游已经可以直接使用 `visual/selectionReason`，优先删除新格式中的冗余解释字段映射，而不是继续制造第二份画面语义。

## 九、新旧格式兼容

- 新运行写入明确的 Planner 输出版本，例如 `plannerOutputVersion: "compact-visual-v1"`，该版本由程序写入，不要求模型生成。
- Adapter 必须继续读取旧项目的 `imagePlan.slots`。
- 新项目读取 `visualPlans`，其中 `visual` 是生成下游 `primaryVisualSubject` 的唯一来源。
- 旧版 `primaryVisualSubject` 只能存在于明确的旧格式读取分支；新版 `visualPlans` 不得回退读取旧字段或跨版本混用语义兜底。
- 同一 Planner 原始结果同时出现新旧两套视觉结构时不得静默合并，应返回明确契约错误，避免重复图片位。
- 旧项目不强制迁移，不覆盖已有计划、图片、候选、Step4决定或用户锁图。
- 下游标准图片位结构保持单一，不允许知识库、审核或 Renderer 同时兼容两种 Planner 原始格式。

## 十、失败开放与禁止兜底

- 单个视觉计划缺失、Query错误、来源错误、Scope错误或重复画面不得触发第二次 Planner 业务规划。
- 能确定性修复的问题只修当前图片位。
- 不能确定性修复时标记当前图片位 `unresolved/needs_user_action`。
- 其他 Planner 图片位、Copy、Image、写回、草稿 Renderer 和 Step4 继续执行。
- 禁止用以下方式让流程表面完整：
  - 默认拿 DAY 第一个 Spot；
  - 用酒店图替代活动图；
  - 用泛化游猎替代明确体验；
  - 用目的地名替代主体；
  - 根据 `subject + action + location` 重新拼接完整画面；
  - 删除缺失的必需图片位；
  - 把 `selectionReason`、`visual` 或旧 `primaryVisualSubject` 塞进 Query；
  - 因进入不同普通 Scope 重新生成、改写或重排 Query；
  - 因局部错误重生成整份 Planner。

- 候选位置数；
- 最终标准图片位数；
- 每个必需位是否有视觉计划；
- 每个unresolved位和原因；
- 每个 DAY 的旧 `dayRoles.primaryVisualSubject` 与新版主图 `visual` 对照，并标记一致、同义等价、不一致或缺失；
- Copy 修改前后 DAY 主题、DAY 正文和图片卡片/Spot 文案的 task payload 与输出对照；
- 每个图片位的 Planner `visual`、下游 `primaryVisualSubject`、选择理由、Query 和 Scope；
- `visual` 是否被 Adapter 原样映射，是否存在任何程序拼接画面；
- Planner Query、Guard 判定、局部修复词、酒店身份补词和每层 Scope 的最终实际请求词；
- 合格 Planner Query 是否被 Adapter、Query Guard/Builder 或普通 Scope 改写、重排；
- 知识库请求数必须为0。

本次记录真实8日行程 Planner JSON 相对基线的长度变化；20%仅作观察参考，不作为硬验收。不能安全合并的旧字段保留，不得牺牲必要输入、视觉决定、解释理由或兼容性来缩短输出。

首次是否直接形成完整JSON必须如实记录。若仍使用技术补救，不得伪装为一次底层模型请求，也不得立即进入知识库测试，应先判断剩余长度来自提示词、非视觉字段还是异常重复输出。

## 十四、验收标准

以下条件必须全部满足：

1. 每份行程只有一次Planner业务规划。
2. 已确认 Copy 真实执行路径依赖旧 DAY 主要视觉，并完成新旧视觉语义对照，不能以字段名称相似代替证据。
3. 新旧 DAY 主要视觉语义等价时，Planner 只输出一次 `visual`，程序将同一句话原样交给图片流程和原本需要它的 Copy 任务；不新增规划或模型调用。
4. 新旧语义不等价或证据不足时，旧 Copy 输入继续保留，任务不得为了精简强行删除或改变文案逻辑。
5. 每个视觉计划保留有效 `visual`，并由 Adapter 原样映射为下游 `primaryVisualSubject`；程序没有第二次理解或拼接画面。
6. DAY主题、DAY正文和图片卡片/Spot文案的实际输入重点与输出行为没有因精简发生非预期变化。
7. 每个视觉计划保留唯一、简短的`selectionReason`，并与 `visual` 职责分离。
8. 单画面校验按自然共现判断，不因一张图包含向导、游客和动物等多个主体而误判。
9. Planner不再输出图片编号、必需性、可移除性、存放位置和比例。
10. 程序能稳定补齐全部确定性字段。
11. 新旧Planner格式兼容，旧项目不受影响，新格式不回退旧视觉字段。
12. Adapter交给下游的标准图片位结构和稳定ID不变。
13. 合格 Planner Query 以原文、原顺序到达知识库请求准备层；普通 Scope 切换不重建 Query。
14. Query 系统只完成新版字段最小接线和不变性验证，没有重写现有已正确逻辑，也没有为清理而扩大修改旧函数。
15. 不合格 Query 只做允许的局部修复；酒店扩大 Scope 的身份补词可追溯且不影响其他模块。
16. Scope 层级、fallback 顺序、知识库接口、`top_k`、Preview-First 和下游候选规则不变。
17. Copy与Image继续并行。
18. 单Slot错误失败开放，不触发整份重规划。
19. Query主体、动作、顺序和地点作用没有因精简丢失。
20. 如实记录真实Excel Planner JSON长度变化，没有为缩短20%删除必要字段或必需视觉计划。
21. 真实Excel无知识库请求dry-run通过，并提交完整报告。
22. 专项测试、Simple Skills、Simple Pipeline、构建和Sites测试通过。
23. 用户人工确认“规划什么图、为什么选、准备搜什么、去哪里搜”后，才能进入知识库全链路测试。

## 十五、停止条件

出现以下任一情况，立即停止继续扩展，不得为了跑通修改下游业务规则：

- 新格式导致稳定slotId改变；
- Step4用户锁图或历史项目读取失败；
- sourceKey无法可靠绑定原始事实；
- 自费、预约或待确认状态丢失；
- DAY主视觉缺失后程序开始猜第一个Spot；
- 新版 `visual` 缺失后 Adapter 根据主体、动作、地点或其他字段重新拼接画面；
- Adapter 生成的 `primaryVisualSubject` 与 Planner `visual` 不一致；
- Query主体或关键动作被Adapter替换；
- 合格 Planner Query 被 Adapter、Query Guard/Builder 改写、同义替换或重排；
- 普通 Scope 切换触发 Query 重新生成或改写；
- 酒店 Scope 身份补词被扩大成其他模块的通用规则，或没有保留 `scope_identity` 来源记录；
- 为了沿用旧代码，让新版视觉计划重新进入案例词表、完整长句回退或旧 Query 生成路径；
- 模块隐藏规则与最低必需视觉冲突；
- Copy与Image由并行退化为串行；
- 尚未证明旧 DAY 主要视觉与新版主图 `visual` 语义等价，就删除 Planner 旧字段或替换 Copy 输入；
- 精简后 Copy 不再收到原有主要视觉语义，或 DAY 主题、正文、图片卡片标题退化为更泛的内容；
- 程序兼容投影对 `visual` 做了改写、扩写或从 Query 反向生成，而不是原样复制；
- 未保存兼容映射前后的Copy task payload和行为对照，就宣称Copy不受影响；
- 为修复结构新增模型调用；
- 知识库、审核、Step4或Renderer被迫兼容两套Planner原始格式；
- 真实dry-run尚未确认就开始知识库请求。

停止后只报告证据、影响范围和建议，不继续扩大修改。

## 十六、交付物

- 新旧格式兼容的Planner输出契约；
- 旧 DAY 主要视觉与新版 DAY 主图 `visual` 的真实语义对照报告；
- Copy 最小兼容投影及修改前后 task payload、DAY主题、DAY正文和图片卡片/Spot文案对照；
- 候选图片位置生成器；
- 新格式Planner校验与失败开放实现；
- `visual` 到下游 `primaryVisualSubject` 的原样映射实现；
- Adapter标准图片位扩展实现；
- 合格 Planner Query 直通、有限局部修复和 Scope 不改词实现；
- 当前 Query Guard/Builder 与普通 Scope 正确行为的不变性证据，以及旧 Query 函数不可达证明；
- 基于现有 Query 记录形成的 Planner原词、修复词、酒店身份补词与最终请求词可追溯报告；
- 相关自动化测试；
- 真实Excel无知识库dry-run报告；
- 修改文件清单、测试命令与结果；
- 剩余风险和待独立复核项。

执行窗口不得自行宣布独立验收通过。完成自动化和真实dry-run后，状态只能写为“实现完成，待用户确认与独立复核”。
