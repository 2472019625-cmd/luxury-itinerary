# Planner Rules

来源：`docs/产品设计/simple-skill-pipeline-四类规则归一.md`  
版本：当前确认版本  
定位：按 Planner 责任拆分后的运行输入与接口规范；内容业务规则仍追溯到 `rules/01—06`，不构成第二套并列业务规则。

## 1. Planner Purpose

Planner 负责：

- 理解本次完整结构化行程及全部正式状态；
- 判断整程产品逻辑、内容主线和视觉主线；
- 判断每个 DAY 的角色和独立重点；
- 判断可选模块显示或隐藏；
- 判断信息层级与内容归属；
- 规划文案逻辑任务、图片位和可并行批量任务。

Planner 不负责：

- 具体文案措辞；
- 实际搜索、下载或视觉筛选图片；
- 修改事实、费用、履约状态或体验状态；
- Reviewer、`review_decision`、finding package、自动 retry、stage budget、自动定向重搜；
- 多层 Reviewer → Agent → Retry 闭环。

## 2. Input Contract

Planner 读取本次行程全部已经结构化的事实及其正式状态，包括但不限于：

- 已确认；
- 待确认；
- `included`；
- `optional_paid`；
- `reservation_required`；
- `pending`；
- 需核验；
- 其他正式状态。

输入必须使 Planner 能识别事实内容、事实来源、正式状态、用户锁定状态和必要上下文。Planner 可以根据状态决定内容放置、显示方式、是否处理、是否保守表达及是否需要后续能力处理，但不得：

- 修改日期、人数、路线、酒店、晚数、餐食、交通保证、费用或其他事实；
- 修改费用、履约或体验状态；
- 把未确认写成已确认、自费写成已含、待核验写成已证实；
- 静默丢弃原始资料中的重要信息；
- 覆盖用户锁定内容或图片。

## 3. 内容层级与模块职责

每条信息先判断所属层级，再决定模块。

- 产品亮点：回答“为什么这整条产品值得客户选择”。
- 行程总览：回答“整程怎么走”，只规划 DAY 主题、路线和确实影响体感的交通提示。
- 臻选下榻：回答“整趟旅行住得怎么样，酒店配置和住宿品质如何”。
- 特色餐饮：回答“整趟旅行有哪些值得期待的特色餐饮体验”。
- 全程交通：回答“整趟旅行会使用哪些主要交通方式，整体移动体验和配置如何”。
- DAY：回答“每天具体发生什么，酒店、餐饮、交通和体验在当天如何展开”。
- 费用与注意事项：负责服务、费用、履约和准备边界。

固定模块顺序为：封面、定制师、旅行元数据、产品亮点、行程总览、臻选下榻、特色餐饮、全程交通、每日细节、费用、预订流程、资金安全、旅行准备与注意事项、固定页脚。

- Planner 可决定可选模块是否显示，但不能改变固定顺序、改名或创建新页面结构。
- 旅行准备与注意事项是固定必需模块。原始资料没有 notes 时，Planner 仍须依据本次已确认事实、目的地信息和正式规则规划一个必需 Copy Task，不得隐藏该模块。
- 有真实住宿事实时显示酒店模块。
- 只有原始资料明确存在且具有特色餐饮价值的体验才显示特色餐饮总览；普通三餐不进入该总览。
- 有每日交通事实时必须形成交通汇总，不能静默隐藏。
- 无适用事实的纯展示字段可以隐藏并使版面收缩，但不能删除事实层数据。
- 自费、可选、需预约和待确认体验可以显示，必须保留真实状态与费用边界。

## 4. 产品亮点来源、数量与质量

产品亮点不是完全由 Planner 自由提炼，按以下优先级汇总：

1. 原始报价单明确标记为海报亮点、海报下方亮点、产品亮点等指定字段的“来源指定亮点”。优先进入产品亮点；可去重、合并同义项、排序和优化表达，但不得改变原始卖点含义，也不得因它对应具体 DAY 就自动降级。
2. 奢游已经正式配置或规则中存在的特殊服务与产品级亮点。只能使用已存在的正式服务亮点，不得创造新的品牌服务承诺。
3. 前两类不足 5 条时，才从本次整程事实补充真正影响购买决策的产品级价值，例如路线组合、跨区域串联、整体酒店组合、整程交通对舒适度和时间效率的提升、行程节奏和贯穿整程的稀缺体验逻辑。

最终目标为 5—7 条：

- 已有 5—7 条时直接使用。
- 超过 7 条时，不得简单截断；按购买决策重要程度、产品差异化、整程级价值、事实依据和重复程度排序、合并同义项并压缩到 5—7 条。原始报价单明确指定的高价值亮点不得无理由删除。
- 不足 5 条时，不得为了凑数将普通单日活动、单项设施、某次热气球、某顿晚宴、某个泳池或某个观景点直接拔高。真实资料无法支撑 5 条时，保留真实结果并返回“产品亮点素材不足”。
- 每条亮点任务必须要求“短标题 + 具体客户价值说明”，讲清楚为什么它让整条产品更值得选择，不能只输出名称或关键词。短标题应简洁、有记忆点，但不能是无意义营销词。
- Planner 最终确定实际采用的产品亮点集合：目标为 5—7 条；真实资料不足时按既定“产品亮点素材不足”规则保留可支持的真实条数。Copy Skill 只负责逐项写好 Planner 已确定的亮点，不重新筛选、增删或排序。

## 5. 跨层表达

- 同一事实原则上进入最匹配的主模块。
- 酒店、特色餐饮和交通可同时承担“整程配置与整体价值”和“当天具体发生”两个职责，因此允许在专业总览与对应 DAY 分别出现。
- 原始资料明确指定为海报亮点或产品亮点的事实，可在产品亮点表达“为什么值得选择这条产品”，并在 DAY 表达“这一天如何发生、客户如何体验”。
- 跨层表达必须改变角度与粒度，不得整句整段复制、说完全相同的话或为填满模块重复卖点。

## 6. 酒店、特色餐饮与交通规划

### 酒店总览

按连续住宿段合并，规划正式名称、有来源的星级/等级/品牌定位、地点或区域、晚数、整体住宿品质和代表性真实空间、景观、服务或体验，建立整趟旅行的住宿品质感。酒店总览不负责解释为什么路线安排住这里、对前后 DAY 有何作用或如何承接某个 DAY；具体入住日和当天情境由 DAY 表达。

### 特色餐饮总览

只规划本次原始资料明确存在、具有特色餐饮价值的餐厅或体验，包括特殊用餐场景、丛林晚宴、海边晚餐、营地特色餐食等，表达类型、场景、氛围和期待价值。必须保留 `included`、`optional_paid`、`reservation_required`、`pending` 等真实状态，不得因自费或待确认直接删除。具体体验日由 DAY 表达。

### 全程交通总览

规划草原飞机、境内航班、专属车辆、游猎车、船只、机场接驳等实际主要交通类别，以及有依据的座位、空间、等级、配置、整体舒适度、时间效率、相较长距离陆路的体验改善和品质感。不逐段展示内部 DAY 路线映射；具体日期、起讫地点和当天方式由 DAY 表达。没有明确车型保证时，不规划具体车型承诺。

## 7. DAY 规划

- 每个 DAY 必须有明确整程角色和独立重点，相邻 DAY 不得只是换词重复。
- 每日细节固定规划主题、路线、节奏、用餐、夜宿或返程安排、正文、最多一条贴士和体验图片。
- 普通单日活动、单项设施、单次餐饮、某次热气球、晚宴、小飞机或观景点默认进入 DAY 或相应专业模块，不能仅因吸引人就提升为产品亮点；来源指定亮点除外。

## 8. Copy Task Output Contract

Planner 输出业务文案逻辑任务，而不是决定物理模型调用次数。标准 7—10 日行程的 DAY 文案优先规划为批量任务，不得默认一个 DAY 等于一次模型请求。

输出支持单模块、多模块和 DAY 批量任务。每批至少包含必要的整程上下文；每个逻辑任务至少提供：

- `targetId`
- `moduleType`
- `facts`
- `factStatuses`
- `plannerGoal`
- `relevantContext`
- `layoutHints`（仅必要时）
- `targetPath`
- `outputSchema`

`targetPath` 使用当前客户行程数据根对象下已授权文案字段的精确点路径，明确结果最终写回的模块和字段，例如 `highlights.0`、`hotels.0.editorialCopy`、`days.2.description`。数组下标使用从 0 开始的稳定索引，不得使用需要 Program 猜测的自然语言位置，也不得指向日期、人数、酒店正式名称、费用状态等确定性事实字段。

`outputSchema` 使用与 `app/config/itinerary-schema.json` 相容的 JSON Schema 片段，明确该路径期望的值结构。Copy Skill 必须按此结构返回 `value`，Program 据此确定性校验并写回。

产品亮点由 Planner 先完成最终选择和排序，再为每一条建立独立逻辑任务及精确 `targetPath`。任务必须保留该条亮点的来源依据和既定卖点含义；Copy Skill 不得获得重新规划亮点集合的职责。多个亮点任务仍可在一次批量调用中处理。

## 9. Image Slot Output Contract

Planner 只回答“这里需要什么图片”。每个 slot 至少输出：

- `slotId`
- `moduleType`
- `required`
- `location`（如适用）
- `hotel`（如适用）
- `activity`（如适用）
- `subject`（如适用）
- `visualGoal`
- `visualContext`
- `copyTargetId`
- `aspectRatio`
- `userLocked`
- `adjacentCopy`（可选；最终 Copy 已存在时可由 Program 补充）

不是所有可选事实字段都必须同时非空，应按 slot 类型提供已有事实。

`visualGoal` 定义这个图片位应该呈现什么。`visualContext` 提供当前 DAY 或模块已有的真实图片语境，包括适用的地点、活动、DAY 角色、已有关键体验，以及前后 DAY 需要避免重复的视觉信息；它不是提前生成的客户文案。`copyTargetId` 关联对应 Copy Task，供 Program 在最终文案生成后建立确定性图文关系。

Image Skill 必须能够仅根据结构化事实、`visualGoal` 和 `visualContext` 完成首轮搜索；图片任务不得依赖最终 `adjacentCopy` 才能开始。因此 Planner 完成后，Copy Skill 与 Image Skill 可以并行执行。

Planner **不得输出** `mustHave`、`prefer`、`forbid`。旧的“Planner 直接生成这三个字段”接口已撤销；它们由 Image Skill 根据当前 slot 事实、`moduleType`、`visualGoal`、`visualContext` 和正式图片规则在内部生成。

- 最低必需图片位为封面 1 张、每个展示酒店 1 张主图、每个展示 DAY 1 张主图，Planner 不得取消或降级。
- 第二张、细节图、装饰图和复合卡图属于可选增量。
- 图片数量根据事实丰富度、不同视觉职责、DAY 角色和版面需求决定，不用关键词机械决定。
- 普通接送、入住、退房和自由活动是否值得视觉展示，由 Planner 判断。
- 只有 DAY 核心视觉职责本身是酒店、入住或酒店体验时，才规划酒店图为 DAY 主图；不得把酒店图作为活动图未找到后的替代。
- 连续多个 DAY 内容相似时，Planner 不得机械输出完全相同的 `visualGoal`。应根据当天地点或区域、已有具体活动、DAY 在整程中的角色、前后 DAY 的视觉职责和整程视觉节奏，优先寻找每一天有真实依据的不同视觉重点。
- 如果原始资料存在不同区域、景观或体验重点，应形成不同 `visualGoal`；如果事实不足以区分，不得虚构某天必然出现的动物、天气、时间段、活动或场景，可以在 `visualContext` 明确“同类活动，需要与相邻 DAY 做视觉差异化”。
- Planner 负责提出差异化目标和相邻重复约束；具体通过环境、行动、主体、景别、构图和视觉职责选择不同真实画面，由 Image Skill 完成。

## 10. Pipeline Exclusions

`simple-skill-pipeline` 不启用 `review_decision`、finding package、多层 Reviewer、Reviewer 发现问题后自动重生成、图片自动第二轮搜索、自动定向重搜、stage budget 驱动业务流程、98% 完成状态、无视觉判断默认 pass、酒店图自动替代 DAY 活动图，以及单个目标失败导致整阶段重跑。
