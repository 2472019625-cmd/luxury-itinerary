## 三、冲突处理顺序

同一领域只允许一个答案，按以下顺序处理：

1. 用户明确确认并已经写入 01—06 的最新决定；
2. 对应领域的 01—06 正式规则；
3. 已有确定性代码、专用提示词、生成后检查和测试证据；
4. 旧规则、任务书、交接和台账仅用于迁移核对与历史追溯。

程序当前行为不能自动成为正确产品规则。若 01—06 与程序不一致，在对照表标为“部分落实/未落实/待验证”，形成后续程序任务；不得为了迁就程序改写产品规则。

## 四、已裁定且不得恢复的口径

- 新智能体只有全部生成阶段完成、实际 2000px 版面检查结束后才到 100% 并进入编辑器；禁止文案完成后提前进入。固定流程的98%修订态仅属于冻结基线，不得进入智能体规则配置。
- 不设置独立图片人工审核页。
- `manual_review` 候选本身不要求清零，但新智能体的必需图片位必须已有真实可用图片才可完成。
- 新智能体的最低视觉覆盖固定为：封面至少1张、每个实际展示的酒店模块至少1张主图、每个实际展示的 DAY 至少1张主图。第二张、装饰图和细节图属于可选位，无合格图时移除并重排；最终保留的每个图片位都必须真实、可解码且具备采用资格。必要性由版本化产品配置和程序判定，AI只能建议可选增量。
- 只有终审成功、达到标准并本地保存的图片可自动入稿；硬拒绝不可采用。
- 生成100%与商业图片授权分开：授权待确认不影响进入编辑器和生成完成状态，但正式导出必须通过独立授权门禁。
- 普通品牌表达建议经用户接受后记为 `user_accepted_suggestion`，它是允许继续的终态但不是 `passed`；事实、费用、履约、安全、内部信息、结构和必需图片硬问题不得使用该终态。
- 旧 `shadow-planner` 的 `review_decision`、finding package、多层 Reviewer、审核后自动重生成/补搜和 stage budget 驱动流程不适用于 `simple-skill-pipeline`。新架构按 Planner → Copy/Image Skills → Program/Renderer 最小职责链执行；确定性安全在正常程序过程中直接保证，单个责任单元失败不触发整阶段重跑。
- 第一批智能体项目全部保留，不提供永久删除、回收站能力或界面承诺；30天回收站只保留为后续方向。
- 自费、可选和待确认体验可成为正文重点或主图，但必须同步真实状态和费用边界。
- 唯一视觉基准是 `assets/references/current-visual-baseline-kenya-8d-2000.png`。
- `行程单满意版本.png` 与冻结旧项目 `design-reference-unified.png` 已废止。

## 六、落实与验收原则

Markdown 是人工规则依据，不会自动被工具执行。每条规则必须在对照表中说明主要执行类型：

- A 程序强制
- B AI生成
- C 生成后检查
- D 人工验收

并标记真实状态：已落实、部分落实、未落实、已过期、无法自动化或待验证。缺少代码、专用提示词、检查、测试或真实证据时，不得标为完整落实。
