# 04 图片搜索与使用规范

版本：3.0
生效日期：2026-09-17
适用范围：图片蓝图、图片位、搜索、下载、审核、采用、去重、编辑器换图、来源与授权、2000px 版面复查。本文是图片领域唯一当前正式规则。

## 已裁定流程口径

- 不设置独立图片人工审核页。
- 后台保留 `auto_approved/manual_review/hard_rejected`，但 `manual_review` 不阻止任务完成或进入编辑器。
- 只有成功完成终审、达到自动采用标准且已保存到本地的图片可自动入稿。
- 可编辑草稿允许必需视觉缺图，但必须在编辑器明确提醒并提供补图入口；最终客户成品不得出现空白图片位。预算耗尽后，非必需图片位从客户版面移除并自动重排。
- 最低视觉覆盖为：封面至少1张真实可用图片、每个实际展示的酒店模块至少1张主图、每个实际展示的 DAY 至少1张主图。第二张、装饰图和细节图属于可选位，无合格图时移除并重排。必要性由版本化产品配置和程序判定，AI只能建议可选增量。
- 生成100%和进入编辑器不以商业图片授权确认为前提；正式导出必须另行通过授权门禁。
- 用户在编辑器选择、上传、移动或清空图片后必须锁定。
- 每个图片位在搜索前确定一份不可变的核心视觉目标和视觉职责，并且只能负责一张能够独立证明全部关键主体与动作的画面。两个可独立发生、可独立找图的动作必须拆成两个图片位；每天最多4张是优先级上限，超过时应取舍，不得为了压缩数量把不同场景硬合并。同一自然画面中的组合主体可以保留，例如象群与雪山、热气球与下方兽群、角马与斑马共同渡河。Query 可以按“精确主体与动作 → 保留核心视觉结果、放宽非核心载体或细节”的顺序逐步扩展，但不得退化为与目标无关的泛词；视觉审核必须复用同一核心视觉目标，不得在后段另换判断口径。未绑定具体身份的体验或氛围图可在核心视觉结果清楚、没有事实误导时标为 `representative`；酒店、专属设施、交通类型，以及以建筑、入口、标识或唯一实体身份为画面目标的景点图仍要求对应身份或类型证据。

## 候选资格的唯一判断口径

- Planner 的 `visual/primaryVisualSubject` 是理想完整画面，不是全部元素同时出现的验收清单。Image Skill 在审核前必须形成 `minimumVisualProof`（最低可用视觉）；它只保留决定“这还是不是同一张图”的 Core：核心视觉主体、缺失后会改变体验类型的核心动作、不可替代的实体或类别身份，以及会造成事实错误的地点/国家/品牌边界。完整视觉描述不得整体转成 Core。
- `Prefer` 表达画面完整度、辅助叙事、时间光线、氛围、构图景别、主体占比、高级感和整程差异。Prefer 只参与评分、排序及 `exact/representative` 区分；缺失本身不得改变可采用资格。
- `Forbid` 只表达已有证据的事实冲突、身份或类别冲突、非真实摄影/禁止素材，以及真正无法用于正式成品的技术问题。不得把“没有达到理想表现”改写成 Forbid。
- 资格与选择分开记录：`eligible` 表示图片真实准确且可以使用；`rejected` 表示命中明确硬错误；`not_selected` 表示图片可用但未成为自动首选。自动首选失败不等于候选需要人工审核。
- `subjectClear=false` 只允许表示 Core 主体已无法可靠识别。主体较小、不是绝对第一视觉中心、景别较远或构图普通只影响 Prefer 排序，不构成硬拒绝。
- 图片内容资格由 Image Skill 形成唯一结果；Step4 只读取该结果并负责展示、选择、上传、替换和移动，不再按自己的内容代码二次升降级。
- Query 优先搜索 `minimumVisualProof` 中可见的核心主体和必要动作；辅助人物、服务过程、陪体物件、环境细节和氛围描述只用于排序，不得默认进入普通 Query。Scope 继续只决定去哪个目录搜索。

## IMG-003—005 图片故事与模块审美细则

本节把仍有效的影像判断写回当前唯一图片规则。它不机械增加图片数量：目标图数用于规划，合格图片不足时按FLOW-004移除非必需位并重排；必需视觉覆盖不得删除或留空。带示例的条款只帮助判断，不要求逐字或逐图模仿，也不能提供新的行程事实。

### 1. 整体影像顺序

候选判断顺序固定为：先核对地点、品牌、活动和主体事实 → 再判断是否符合模块职责 → 再比较品牌质感和客户想象空间 → 最后检查裁切与整程节奏。漂亮不能抵消事实错误，官方来源也不能抵消主体错配。

最终图片故事应同时追求：高端与私密感、自然真实、快乐松弛、构图与清晰度品质、目的地或体验辨识度。至少有一个可说明的客户价值和一个具体事实主体，不能只依靠“豪华氛围”。

### 2. 色调、光线、人物与场景

- 优先自然采光、日出日落、柔和侧光或克制室内暖光；色彩可浓郁但不过饱和，天空、海水、植被、木石等自然色应稳定耐看。
- 强滤镜、荧光色、过度 HDR、灰脏、死白、明显噪点、闪光灯直打和严重曝光异常至少降低为 `manual_review`；已造成严重低质、失真或主体不可辨时才按证据进入 `hard_rejected`。
- 人物应自然、放松、得体并与场景发生关系；服务人员应着装整洁、动作专业。自拍大头、游客打卡、尴尬裁切、疲惫焦虑、争吵、抽烟酗酒、过度性感化或明显表演感不得自动入稿；无明确硬伤但品牌不适配时保留为 manual 供人工判断。
- 室内重材质、秩序、干净度和服务细节；室外重主体、尺度与目的地辨识度。明显 AI 感、超现实、严重畸变、杂乱拥挤、低档设备或卫生疑虑属于禁止方向。
- 上述主观项由视觉模型排序、生成后整体复查和人工审美共同负责；没有可验证硬错时不得仅凭“高级感不足”把候选记为硬拒绝。

### 3. 模块正反例

- 封面：优先整程最具代表性的目的地大场景、稀缺体验或标志性住宿与环境关系，并保留标题安全区。普通卧室、Logo、拥挤街景、自拍、主体过小或与整程无代表关系的局部图不适合作封面。
- 酒店：优先酒店身份可核验的外观、客房与景观、私人露台、泳池、餐厅、水疗或特色公共空间；图片须证明“为什么值得住”。其他酒店、门头/Logo、普通风景、老旧杂乱空间和低清官方小图不得冒充目标酒店价值。
- 特色餐饮：必须看见对应餐饮形态、餐桌、餐食、服务或真实用餐环境。酒窖/品酒、丛林早餐、星空/Boma/Bush Dinner、主题烤肉等只在本次事实存在时作为搜索类型；普通门头、大堂、树景、空镜或不对应的普通餐桌不能替代。烟熏炉火、油腻摆盘、脏乱桌面和卫生疑虑为重点拒绝项。
- 交通：必须一眼识别正确交通类别。商务车可表现外观、内饰和座椅空间；游猎车可表现开顶或同等级车辆及观察/摄影场景；草原飞机可表现轻型飞机、登机、跑道或空中衔接；船只可表现船型、登船或航行。酒店大堂、机场大厅和纯风景不能替代工具主体，未保证品牌/型号不得形成承诺。
- 每日体验：优先当天核心活动、参与方式和与其他 DAY 不同的视觉记忆点。普通风景不能替代明确游猎、飞行、浮潜、文化参观、晚宴等活动；同日多图应分别承担 environment/action/detail/transition/closing 等不同角色。
- 复合体验：最多两图且各自有 `label`；例如外观与内饰、环境与餐食，只是帮助理解的结构示例。若 2000px 中任一主体不可辨认，应拆卡或只保留强项，并移除多余图片位后重排，不以留空或增加小图数量补偿。

## IMG-006—010 搜索规划、收集与记录细则

### 1. 应搜与不应单独搜索

- 图片蓝图优先规划封面、核心酒店/营地、有独立展示价值的特色餐饮、关键交通工具和每日核心体验；自费、可选、待确认体验按销售价值和事实依据参与规划，同时保留状态与费用边界。
- 普通早餐、午餐盒、普通酒店晚餐、无独立价值的接送/入住/退房/自由活动、与已有图片位表达相同的重复体验，以及原始行程未出现的推测体验，不独立建立搜索任务。
- 上述清单是规划优先级，不是“每类必须找到一张”的机械数量门槛；最终图片位数量与必要性分流服从IMG-003、FLOW-004，客户成品不得保留空白图片位。

### 2. 查询词与知识库范围生成

#### 精简 Planner 契约（2026-09-16确认，实施待验证）

本小节在 `simple-skill-pipeline` 新格式中替代下文旧 Planner 输出字段要求；旧项目读取与下游标准图片位字段继续兼容，不迁移或覆盖旧项目。

- Parser 整理原始事实，程序先建立候选图片位置；Planner 单次业务规划选择保留位置，并输出 `visualPlans`：`targetKey/sourceKey/visual/selectionReason/subject/action/identity/location/locationRole/queries`。程序补齐稳定编号、必要性、可移除性、比例、位置和完整来源绑定，不能重新决定画面。
- `visual` 是完整画面的唯一决定，Adapter 原样映射到下游 `primaryVisualSubject`，不从主体、动作、地点重新拼句。`selectionReason` 解释为什么选择，永不参与 Query。DAY 主视觉与各图片卡的兼容分发服从03，本轮不能安全合并的旧字段保留。
- 一张画面按自然同框判断，不按主体数量拆分；向导带游客徒步、旁边有斑马可以成立。仅明确二选一或不能在同一自然画面成立的独立场景需要标记问题，不新增复杂拆分系统。
- 合格的2—4条 `queries` 按原文、原顺序接入现有 Query 路径；只接线与验证，不重写已正确逻辑。普通 Scope 切换复用基础 Query；现有酒店扩大范围补完整酒店身份的例外保持不变。Scope层级、fallback、top_k、知识库接口、Preview-First及后续流程不变。
- 失败只影响当前位；不新增模型调用，不为局部问题重规划。一次业务规划之外，仅沿用已确认的“未形成可用完整JSON时最多一次底层技术补救”，分别记录业务次数和底层请求次数，业务校验失败不得触发补救。
- 本轮先完成无知识库 dry-run 并停下供用户确认；不下载、不审核、不写入真实候选、不部署、不正式渲染。

- 知识库检索先判断图片用途，再一次性生成 `Query Plan` 与 `Scope Plan`。用途统一分为酒店主图/空间、酒店餐饮或专属体验、DAY/目的地体验、明确景点或餐厅实体、交通、封面六类；示例只用于验收，不得把国家、酒店、DAY或当前项目写死进规则。
- Planner 是图片画面的唯一决定者，并在现有规划调用内为每个封面、酒店、餐饮、交通和 DAY 图片位同时输出：`primaryVisualSubject`、拆好的 `queryCore.subject/action/identity`、`location`、`locationRole`、第一条 `fidelityQuery` 和 1—3 条 `alternateQueries`。每个图片位必须是一张能直接拍出来的具体画面；禁止“A或B”、抽象抵达/离境/入住/用餐/接送概念，以及两个可独立找图的体验。相同体验跨模块可以重复出现，但各图片位必须承担不同的可见主体、动作或视觉职责。
- Planner 每份行程只调用一次，空响应、非法输出或业务校验失败都不得触发第二次整份规划。程序可确定处理的格式、Query 清洗和辅助位标记只修当前 Slot；重复职责、抽象画面、缺失关键语义或其他无法可靠判断的问题只挂起当前 Slot。挂起 Slot 不执行自动搜索，但必须带着原因进入 Step4；其他图片位、Copy 和草稿生成继续运行。
- Query Builder 只执行 Planner 已确定的搜索意图，不重新决定主体。Planner 的第一条保真 Query 只要非空、简短可搜索且不含说明性废话，就按原顺序保留；不得因为“象群/大象群”“渡河/横渡河流”等文字不完全一致而判错或改写。只有 Query 少于2条、过长、含说明性文字或不合格时才兜底；兜底只能用 Planner 已拆好的主体、动作和必要身份重新组合，禁止再次读取完整 `primaryVisualSubject` 生成 Query，也禁止按固定字数截断。两条准确 Query 已经足够，不强行凑满4条。
- `locationRole=scope_only` 时地点与目录身份只参与 Scope、来源路径和后续审核，不得进入普通 Query；`locationRole=visual_identity` 时地点、建筑、入口、标牌或命名实体本身就是画面身份，可以保留在 Query。该判断只读取结构化字段，不通过某个国家、地区、动物、活动、酒店或景点的专用删除词表推断。`visualGoal/visualDuty`、相邻图片差异说明、时间氛围与费用状态永远不能参与 Query；进入知识库前仍统一清除意外混入的说明性文字。
- 知识库 Query 保持2—4条、去重并按 Planner 顺序执行，通常中文精准表达在前、英文同义表达在后；每条只使用一种语言。禁止使用 `landscape/experience/view/activity` 等无意义泛词凑数。若 Planner Query 与 queryCore 均无法形成可靠短词，则该图片位标记 `unresolved/needs_user_action` 并保留到 Step4；不得把完整画面长句发给知识库，也不得中断其他图片位、Copy、Step4或整份行程。
- 酒店模块先锁定具体酒店根目录，只在该酒店目录内按“外观、套房、泳池、公共空间”等高价值类别逐条查询并建立同一候选池；Scope 已证明酒店身份时 Query 不重复酒店名。找到明显合适的酒店代表图即停止，不要求查完所有类别。具体酒店目录无法定位、明确为空或不可用时立即停止知识库，不扩大到地区或国家，交给既有 Web 来源继续处理。DAY/体验图不使用这套酒店候选池规则。
- DAY/目的地体验按“当前真实地区 → 当前国家”逐级放宽；明确景点或餐厅按“实体所在地区 → 当前国家”放宽但实体身份不变；交通按“地区 → 国家 → 根知识库”放宽；封面按本次行程核心目的地优先，再到国家。不得跨国家误配。
- 在既定 Query Plan 与 Scope Plan 内按 Query 顺序逐条收集知识库 preview；每条 Query 返回后先按真实素材身份合并去重，再按低成本排序动态分批审核，每批最多4张。出现 exact 或明显高质量 eligible 时立即停止，只有未达到停止条件时才审核当前候选池下一批。当前候选池全部处理仍无 eligible，才依据 `scope_state` 决定继续：`no_match` 可执行下一 Query，普通图片位同一 Scope 默认最多2条；`empty/unavailable` 立即进入父级 Scope，酒店模块结束知识库。所有已返回 preview 均进入 Step4 候选池并保留审核状态，不得设置客户端候选条数截断。整个过程仍属于同一 Image Slot、同一个 Image Skill 业务批次，不新增 Stage、Planner、Reviewer、retry 或 follow-up round。
- 视觉审核完成后统一排除硬拒绝并比较合格候选；只有最终自动采用图或用户在 Step4 明确选择的候选才下载对应 `matched_file` 原件。其他候选保留本地 preview 和审计状态，不得提前下载原件；原件下载失败必须与知识库无匹配分开记录。
- `source_paths` 对酒店、餐厅、专属设施，以及以建筑、入口、标识或唯一实体身份为画面目标的明确景点是硬证据，视觉判断不得覆盖实体冲突。命名景点如果只是体验发生背景，而真正要看到的是可由画面直接证明的通用活动，则按 DAY/目的地体验处理；实体名只帮助Scope解析和后续审核，不进入知识库Query。普通活动、动物、餐饮体验、风景和交通同样由Scope约束搜索范围，由核心主体与动作约束画面内容。搜索阶段与审核阶段必须使用同一图片用途分类。
- 公网检索继续使用适合网页搜索的正式实体、来源和场景表达；知识库短查询规则不得删除或替换现有公网搜索能力。

### 3. 来源与网页提取

- 来源顺序细化为：用户原始/已授权素材 → 运营方官网及官方媒体/press/gallery → 旅游局或目的地官方媒体 → 可信酒店联盟/行业组织 → 授权信息清晰图库 → 可信媒体/供应商 → 其他第三方。来源优先级只影响可信度和排序，不代替主体审核和商业授权。
- 官网身份按品牌官方域名判断；页面标题、URL 路径或正文出现品牌名不足以证明官网。官方社交媒体、联盟或媒体来源仍应记录平台、账号/页面和可追溯地址，不伪标官网。
- 网页提取优先 `og:image`、`twitter:image`、`srcset` 最大尺寸、懒加载字段、JSON-LD 的 image/photo/contentUrl 和正文中有明确 alt/title 的图片；排除 Logo、图标、头像、二维码、sprite、追踪像素、重复 URL 和无来源页的孤立图片。
- 技术硬门槛保持 IMG-009 的 900×500、14MB 和比例范围；排序时优先 1600px 以上，2400px 长边可作为正式大图素材偏好，但不得因未达到偏好而单独硬拒绝。

### 4. 低成本排序、审核与缓存

- 低成本排序优先官方/授权可信来源、页面主图、高分辨率、标题或 alt 命中主体以及适合槽位的横向比例；具体权重是程序实现参数，不升级成跨模块统一硬门槛。
- 初审统一比较 relevance、luxury、cleanliness、composition、watermark；终审先描述实际主体，再按当前slot的结构化Core分别判断主体、核心动作、必要身份和事实边界。每一张候选必须独立满足该图片位的Core，不得用同批另一张候选补足；具体动作是否属于Core只能根据“缺少后体验类型是否改变”判断，不维护活动关键词硬表。评分与Prefer只用于排序和 `exact/representative` 区分，不能改变资格。
- 搜索/页面候选缓存至少由标准化查询、地点和主体区分；图片文件以 SHA-256 去重；终审缓存至少包含图片哈希、模块、模型与 `mustHave/forbid` 规则指纹。地点、主体、硬规则、蓝图、模型或规则版本变化时，相关旧审核结果必须失效。
- 缓存用于减少成本和重复请求，不能默认跨项目复用同一成片，也不能覆盖用户锁定、最新事实和当前规则。

### 5. 去重与内部账本

- 文件相同用 SHA-256；缩放、压缩和轻裁切的近似图使用 dHash/pHash。当前程序 dHash 汉明距离 `≤ 8` 作为视觉近重复参数；同场景连拍、相似机位和跨模块同义画面仍需视觉复查。
- 每个候选的独立记录至少包含 record/candidate ID、稳定素材身份、slot、轮次、查询词、preview 与 matched_file 关系、本地 preview、按需下载的原图、来源页/标题/类型、官网标记、许可/创作者（可得时）、尺寸、SHA/dHash、初审/终审分数、状态、阶段和理由。
- 失败记录至少包含 slot、实际查询、失败阶段、原因、尝试次数和下一动作；不得静默丢弃。来源与审核字段只在内部账本和编辑器候选详情使用，客户结果继续服从 IMG-020。

## 图片智能体用途与责任

- 任务规划：读取整程事实、视觉主线、真实 layout slots 和用户锁，决定哪些位置值得搜、优先级和不同视觉角色；不得创建新页面、改文案事实或覆盖锁图。
- 图片搜索：按 slot 输出查询、来源优先级、候选和失败记录；允许放宽软偏好，禁止放宽地点、品牌、主体、水印、下载安全和全局去重。
- 图片审查：输出三态、实际主体、来源/视觉分离判断、分项分数、理由和硬拒绝证据；系统异常转 manual，不推断图片有硬错。
- 生成后审查：在实际 2000px 中检查图文对应、重复、色调、顺序、裁切、双图职责和空白，只处理失败 slot，不重写整份行程。
- 失败动作：预算结束后可选位移除重排；封面、每个展示酒店和每个展示DAY的最低主图缺失时生成可编辑草稿并在编辑器提醒，未补齐不得100%或正式导出。manual候选可保留，硬拒绝不可采用；授权不明不影响生成100%和编辑，但正式导出门禁保持关闭。产品已明确禁止AI生成图片兜底。
- 最终责任：程序负责 slot、预算、技术安全、三态、去重、锁定和客户隔离；AI 负责受限规划/排序/视觉判断；用户负责 manual 采用与自有素材；人工负责整体审美和商业授权。

## 图片位完成状态

### Simple Pipeline：知识库到 Web 的受控接续（2026-09-18）

Planner在原有调用内先区分“主体动作正确”与“具体身份不可替代”，再填写现有布尔值，不新增输出字段或模型调用。活动、自然现象、场面及营销名称不等于唯一实体身份；重要卖点不等于身份必需。独立酒店模块展示预订的具体酒店，其他酒店不能替代，因此必须true并写正式身份；目录缺失沿用零图片查询转Web的既有策略，不扩大找相似酒店。

Planner的`exactIdentityRequired`收窄标准：只有“如果不是这个具体实体，即使主体和动作都正确，也会造成事实错误”才为true。地点只是体验发生背景，图片主要展示主体与必要动作时必须false；原始行程地点准确不等于照片必须证明唯一地点身份。identity非空、地点明确、locationRole为visual_identity、主体/动作或交通类别必须正确，都不能单独推出true。此判断不得依靠实体类型、地点或活动关键词。Adapter只校验透传；普通体验先按既有Knowledge地区Scope检索，明确身份位先定位精确实体目录，目录不存在或无法解决才进入既有Web，不在地区范围找相似实体。此修正只改Planner判断说明，不改Query、目录策略或审核标准。

Web下载前先执行资源技术过滤与缩放归并，再用当前最低视觉及queryCore检查代理URL解包后的完整资源pathname、alt/title、图注、图片级structured metadata和图片绑定的局部上下文。相关性分strong_match、explicit_mismatch、insufficient_evidence三态；只有明确冲突可以因相关性过滤。证据不足不是错误，按正文/gallery、主体动作命中、实体专属页路径及现有来源/质量分择优进入累计下载预算内的小候选池，交现有Vision判断，不全下载。exactIdentityRequired为true时实体依据可由局部说明、专属页/section/gallery及资源路径共同支持，不逐字验收复合identity；false不因缺地点文字拒绝。页面标题、摘要、目的地及来源可信度只能辅助排序，不能单独宣称照片内容正确。filtered_before_download不占下载与视觉预算。下载器不承担语义判断。

Vision单次最多四张不等于Slot总共四张；在现有累计下载/审核预算内继续下一批，只有真正selected且满足现有早停条件才停止。记录相关性三态数量、证据不足进入下载池数量、逐批Vision数量及最终selected。此规则不改变Query、页面预算、Planner、Knowledge或Core/Prefer/Forbid审核标准。

Web页面预算区分累计页面访问与真正产出门禁合格候选的素材页面。失败/空提取/无相关候选页面不计有效素材页；整个Slot访问与下载预算不重置，尚有后备Query时保留至少一次页面和下载机会，不机械平均分页。记录逐Query提取、技术/缩放/相关性过滤、下载、审核及采用漏斗；不改变Query、Knowledge、视觉审核和后续模块。

本轮 Web 收口：Planner每个图片位只新增boolean `exactIdentityRequired`。true唯一表示图片必须证明目标具体实体身份，否则相似内容也不合格；false表示具体实体不必被证明、可只作背景。Planner只按去掉具体身份后是否仍能完成主要展示职责判断，不靠名称/类型关键词。Adapter只校验及原值透传，缺失、非boolean或true但identity为空只标记当前位，不推断、不重规划。fast path唯一触发条件为非空`queryCore.identity`且`exactIdentityRequired === true`，酒店、locationRole、最低视觉其他旧标记均不得另行触发。既有实体映射仅在触发后解析正式名称、目录别名与记录类型，不参与必需性判断。Web true保留正式实体名、优先已有identityEn；false以主体动作及必要地区/国家背景为主。英文首词与中文/混合后备维持逐词处理、成功早停；不增加模型调用，不改Knowledge词。Web下载前资源过滤、同原图缩放归并及日志不占下载/审核预算保持不变，安全下载和审核口径不改。

- 明确实体/酒店专属体验仅在具体身份已被结构化语义确认为Core时采用 `explicit_entity_fast_path`；不得以实体名、类型关键词或 `locationRole` 推断Core。只查询验证匹配的实体/酒店目录；无法定位时零查询进入既有Web，不将地区/国家目录当成实体目录。通用体验的渐进Scope策略不变。当前历史Planner记录缺少身份Core标记的兼容问题必须单独报告，不以名称兜底。
- 精确目录内仍先处理当前候选；`empty/unavailable`立即停止，`no_match`或候选全部明确不合格时最多尝试两条Query后进入Web。酒店代表图保留最多四个既有高价值类别及早停规则。身份未知或审核异常/不完整仍留人工，不能冒充内容未命中。
- 实体Web使用完整实体名、现有短核心Query及至多一个地点背景；酒店专属体验绑定完整酒店名，不拼回理想长画面。记录命中路由、实体类型、Knowledge停止原因、进入Web、实际Web词和最终来源；目录定位失败记为blocked而非completed。

- 保持同一Image Skill、同一图片位、单轮业务批次。无内容/无合格候选允许内容兜底；failed/timeout允许服务降级兜底，分别记录原因。目录无法定位但目标实体已知可进入Web；身份不明、Query不安全、审核失败/超时/不完整保留人工状态，不用扩搜掩盖。
- Web只补结构化实体及目的地身份，不从完整理想画面猜主体。酒店用完整酒店名加外观、套房、泳池、公共空间最多四类；普通图片位最多两条核心Query，明确酒店专属体验才绑定酒店名，普通体验不因入住酒店而锁酒店。
- Query逐条执行，受控候选池按每批最多四张审核；同批合格图排序后选择。普通representative继续查看池内下一批，exact或现有高质量eligible条件可早停。采用去重失败则尝试池内下一张，不追加业务轮次。
- 网页和下载候选预算按图片位累计，不随Query重置；沿用原有技术重试和下载安全。保留返回候选、未审核/未下载及下载失败记录，知识库策略、审核标准、Preview-First、Step4及Renderer不变。
- 分别记录Knowledge/Web阶段墙钟耗时与Web各操作累计耗时；并行操作耗时不能相加解释为总耗时。本轮模拟Image-only回归不作为真实联网性能结论。

`simple-skill-pipeline` 每次自动执行只进行一轮完整的 Image Skill 业务批次；批次内部完成多搜索表达、允许来源并发、候选合并、去重、技术过滤、主体判断、排序和选择。批次结束后不得自动启动第二轮或由 Agent 定向补搜；未找到时返回 `not_found/needs_user_action`。只有用户主动要求重新搜索目标图片位时，才创建新的独立搜索请求。相同文件指纹、相同图片位和相同规则版本可继续复用缓存，避免重复处理。

最终仍显示的图片位只有在自动采用真实本地图或已有用户锁定真实可用图片时才视为完成。最低必需位由程序按版本化配置确定：封面1张、每个展示酒店模块1张主图、每个展示DAY 1张主图；AI不能改写必要性，只能建议第二张、装饰图或细节图等可选增量。一轮批次未找到后，可选位必须从客户版面移除并触发重排；最低必需位进入带提醒的可编辑草稿，直到用户采用可用候选、上传已授权素材或主动发起的新搜索成功。候选库状态不能让缺少真实可用图片的必需位自动完成。草稿编辑界面可以显示待补图位置和提醒；任何正式客户预览或正式成品不得显示空白框、占位图、不合格图、硬拒绝图或AI生成图。
