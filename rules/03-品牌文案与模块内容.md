## AI职责边界

### Planner 精简时的输入兼容（2026-09-16确认，实施待验证）

- 本轮只减少 Planner 重复输出，不改变 Copy 的选题、写作、事实与状态规则。DAY 主题、正文继续按原有需要接收当天主要视觉及完整必要上下文。
- 每张图片卡及对应体验文案必须接收自己绑定图片位的完整画面；DAY 辅助图不得复用当天主图冒充自己的画面。未绑定图片位的普通 Spot 文案保持原有事实输入。
- 仅在旧 DAY 主要视觉与新版 DAY 主图 `visual` 已证明等价时，程序才可原样复制同一句话给两个使用方；不新增模型调用，不重新理解或拼接。无法证明等价时保留 `dayRoles.primaryVisualSubject` 和旧 Copy 必要输入，不执行字段删除。
- 图片 `visual` 原样传递给该位的 `visualSubject/primaryVisualSubject`。来源、图片位置、标题对应、自费/预约/待确认状态不得因精简丢失；不能把整份视觉计划或搜图词替代文案事实。
- JSON 缩短比例仅记录，不是牺牲兼容性的硬门槛。未完成输入前后对照不得宣称文案行为不变；无知识库 dry-run 只验证输入，不等同于实际文案生成验收。

- 客户文案模型只接收允许的事实字段和本文件对应的专用提示词。
- AI 不读取全部 Markdown，也不能把输出当作事实来源。
- 文案不合格优先局部重写；事实或费用冲突必须返回用户，不得通过改写掩盖。

## COPY-001—COPY-017 运行细则

以下细则是上表规则的正式组成部分，承接《奢游品牌表达规范》中仍有效、会影响客户结果的要求。旧规范仅供迁移追溯，程序、提示词、检查器和验收均以本节为准。

### COPY-001 品牌人格与表达顺序

- 结构数据负责完整，Copy 负责选择。客户文案不是源资料、Planner facts 或 `verifiedFacts` 的完整摘要；先判断当前模块要回答的客户问题，再选择最值得客户看到的少量事实。
- 每段只突出一个主价值，必要时增加一个辅助价值。真实但与当前模块核心客户问题无关的事实可以不进入正文，不得用“完整复述”代替内容判断。
- 文案同时完成三个目标：让客户产生抵达向往；理解路线设计和服务价值；看清费用、安全与自然边界，但不能先看到免责条款。
- 写作者定位是“高端定制旅行产品内容营销写作者”：懂资源、路线和客户购买决策，但不是供应商资料复述员、百科编辑、官网翻译员、旅行散文作者或口号生成器。
- 文案丰富度必须来自“真实事实 + 合理体验化展开 + 客户价值”。可基于已确认地点、活动、酒店、住宿形态、交通、节奏与服务方式，说明客人会如何感受和为何值得；只要不改变产品边界，不要求 Excel 存在完全相同原句。
- 每句话至少承担一种信息职责：A. 提供事实；B. 解释体验如何发生；C. 说明对客户的价值。连续形容词、隐喻和情绪句如果没有任何一项职责，属于低信息量文学化表达。
- “荒野注解、低语世界、触摸脉搏、正确打开方式、震撼”等散文化套语如果没有新增事实、体验方式或客户价值，必须删除，不得用来填充篇幅。
- 每段只突出一个主要高潮，先写客户可感知的场景和动作，再解释稀缺价值与专业安排，最后用服务型语言说明边界。
- “野奢、私享、深入、守候、沉浸、第一排视角、自然剧场”等词只能在具体事实和场景支撑下使用，不能以形容词替代内容。
- 禁止说明书、百科、廉价促销、供应商操作和推责免责口吻；不得出现“超值、必冲、打卡、网红爆款、性价比拉满、后果自负”等表达。

### COPY-002 模块职责与阅读顺序

- 固定顺序中的模块职责为：产品亮点回答“整条产品为什么值得选择”；行程总览回答“整程怎么走、每天是否含餐”；臻选酒店回答“整趟旅行住得怎么样，酒店配置和住宿品质如何”；特色餐饮回答“整趟旅行有哪些值得期待的特色餐饮体验”；全程交通回答“整趟旅行会使用哪些主要交通方式，整体移动体验和配置如何”；DAY 回答“每天具体发生什么，酒店、餐饮、交通和体验在当天如何展开”；费用和注意事项负责服务、费用和准备边界；关于我们与联系我们负责品牌背书和联系入口。
- 每条信息先判断内容层级，再决定主模块。同一事实原则上进入最匹配的主模块；酒店、特色餐饮和交通事实可因同时承担“整程配置与整体价值”和“当天具体发生”两个真实职责，在专业总览模块与对应 DAY 分别表达。跨层引用必须改变表达角度和信息粒度，禁止整句整段复制、说完全相同的话或为了填满模块重复堆砌。
- 酒店、餐饮和交通先于 DAY 细节展示；全局安全与履约边界集中到尾部，不能在每天反复警告。

### COPY-003 封面主标题

- 结构为“目的地 + X天X晚 + 产品形态”，目的地和天数晚数来自确定性事实。
- 不写具体人数，不用“定制团、私家团”冒充产品形态；标题必须单行可读，超长时先压缩修饰语，不能删除目的地或天数晚数。

### COPY-004 封面副标题

- 副标题是一条整程销售叙事，回答“这是一条怎样的旅程、核心体验组合是什么、最终形成怎样的旅行结果”。优先从 Planner 整程主题、来源指定亮点、DAY role 中最有辨识度的 2—3 个整程锚点及最多一个重要配置中选择，不要求覆盖全部真实信息。
- 副标题是完整叙事，不是把草原飞机、酒店、用车、全包等卖点用逗号重新排列；封面控制为2—3行且不超过76字。
- 不照抄供应商副标题；没有足够事实时使用克制短句，不用“顶级、尊享、非凡”等空泛词堆叠；不强制使用某几个固定连接词，只检查真实语义推进和收束。

### COPY-005 产品亮点

- 第一优先汇总原始报价单明确标记为海报亮点、海报下方亮点、产品亮点等指定字段的内容。这些属于“来源指定亮点”，应优先进入产品亮点；可以去重、合并、排序和优化表达，但不得无依据改变卖点含义，也不得因其中出现热气球、游猎、小飞机、晚宴等具体体验就自动降级为 DAY。
- 第二优先加入奢游已经正式确认的特殊服务/产品级亮点，只能使用正式配置或规则中已有的服务亮点，Planner 和 Copy Skill 不得自行创造。
- 当前两类汇总后不足5条时，Planner 才可以从本次整程事实中补充第三类亮点。补充项必须是真正影响购买决策的整程级、路线级或产品级价值，例如路线组合、跨区域串联、整体酒店组合、整程交通对舒适度和时间效率的提升、行程节奏或贯穿整程的稀缺体验逻辑。普通 DAY 体验不能仅因吸引人被随意升级。
- 每条采用“短标题：客户价值”的完整表达，裸写“顶奢连住、私人保护区、一价全包”等标签不合格。
- 一条亮点只讲一个购买理由。标题负责记忆，正文只解释这个理由为什么重要，不继续叠加第二、第三个独立卖点。
- 公司优势必须转化为客户结果，例如“一家一团：路线节奏由同行人决定”，不能只写口号；路线亮点必须说清具体场景、稀缺性或节奏价值。
- 各亮点不得换词重复；自费、可选或待确认亮点必须同时带真实状态与费用边界。
- 最终产品亮点目标为5—7条。汇总后已有5—7条时直接使用；超过7条时，按客户购买决策重要程度、产品差异化、是否属于整程级价值、事实依据和与其他亮点的重复程度排序、合并同义项并压缩到5—7条，不能简单截断，原始报价单明确指定的高价值亮点不得无理由删除。
- 不足5条时不得为了达到数量目标，把普通单日活动、单项设施、某次热气球、某顿晚宴、某个泳池或某个观景点直接提升为产品亮点。真实资料确实无法支撑5条时，保留真实可支持的亮点并返回“产品亮点素材不足”，不得虚构或强行拔高。
- 每条亮点必须包含“短标题 + 具体客户价值说明”。短标题保持简洁、有记忆点，但不能为了短而退化成无意义营销词；正文必须说明这个亮点为什么让客户更值得选择整条产品。结构示例只用于说明完整度，不得固化成正式文案。
- 来源指定亮点即使对应具体 DAY，也可同时在产品亮点表达“为什么值得选择这条产品”，在 DAY 表达“这一天具体如何体验和发生”；两处必须改变角度和粒度，不得整句整段复制。

### COPY-006 行程总览与每日主题

- 每日主题是当天最值得记住的一句话钩子，不是全日摘要；从 `dayRole`、相邻日差异和当天真实体验中选择 1 个主记忆点，最多带 1 个辅助点，写成标题式短句。
- “全天游猎、抵达、转场、返程、自由活动、前往某地”等纯动作不能单独充当主题，但动作与当天独特体验或旅行变化结合时可以使用；酒店名不能单独充当主题。
- 总览仅保留 DAY、主题、A → B → C 路线和确实影响体感的长车程、内陆飞、出海或轮渡提示；删除重复三餐、酒店长名、长说明和过多标签。
- 主题与路线先由确定性骨架提供约束，再由模型表达；主题不合格只重写目标 DAY，不得重写整份行程。

### COPY-007 臻选酒店

- 臻选酒店是整趟旅行住宿配置的总览。数据层保留 `officialName` 作为内部正式实体名，`shortName` 作为当前 locale 的客户展示名。客户卡主标题使用 `shortName/displayNames[currentLocale]`；第二行只在与主标题不同时保留原始 `officialName`，作为官网、Google 或 OTA 查询用的低权重辅助信息。行程总览、当日路线、当晚入住和 Visual Card 不重复展开长官方名。
- 当前 locale 没有已确认展示名时使用 canonical/officialName 兜底并标记 `entity_display_name_missing`，不得让 Copy 临时翻译、自行音译或创造新名称。展示名只用于客户层，不得替代 Facts Research、Image Search、知识库 API 或 `searchIntent` 中的内部正式实体名。
- 酒店正文固定为 2—4 句直接陈述：第一句说明酒店是什么及位于哪里；随后选择 1—2 个最值得记住的真实住宿特点，并分别说明它们带给客户的住宿价值；最多用一句轻量说明旅程开场、深入区域、连住节奏或城市收束等产品角色。每句话只承担一个主要功能，少用长并列句，不用情绪化收尾替代信息。
- 禁止设施清单、翻译腔、供应商宣传和无依据的奢华形容；应从真实信息中选择最能建立整体住宿价值感的内容。
- 酒店设施、位置、景观、餐厅和活动必须逐句引用供应商资料、用户确认或带来源与核验记录的酒店官方事实；图片搜索结果只用于选图，不能仅凭照片判断设施事实。已核验的泳池等住宿设施可用于酒店模块及相关入住 DAY，但不得据此扩写无依据动物场景；房型、餐食和替换状态不得被写成情绪化承诺。
- 酒店正常生成路径是：酒店名称 → Copy Facts Research 一次检索位置、客房、设计、设施 → 优先核验实体官网、品牌官网、官方 Fact Sheet 或品牌新闻稿 → 官方缺失的字段再核验 DATA-001 允许的受控外部来源 → `verifiedFacts` → Copy 从中选择最有价值的 1—2 个事实 → 转换成客户住宿价值表达。最多使用两个不同的受控外部页面；同一酒店 `editorialCopy` 与 `proofPoints` 共用同一次研究结果。`verifiedFacts` 是酒店外部客观事实的候选素材池，不要求全部写进正文。
- 同一次研究结果同时由程序确定性映射为 `factRows[]`，固定顺序为位置、客房、设计、设施。成功字段直接使用已核验 `fact`；未找到或来源不可用的字段保留空文本及内部状态，客户展示时隐藏。该映射不新增 Copy Writer 请求，不从 `editorialCopy` 拆句，也不允许 Adapter 再次理解或改写事实。现有 `editorialCopy/proofPoints` 继续保留，避免前端接入前改变旧版展示。
- 研究结果按字段记录 `success/not_found/source_unavailable`。单个字段缺失不拖垮整家酒店；最终 `verifiedFacts = 0` 时，必须记录“酒店事实研究未获得可核验结果”，不得依赖模型常识新增酒店设计、设施、景观、服务或房型事实。只能使用原始供应商资料已经明确存在且属于当前酒店的事实；如果原始资料也只有酒店名、地区、晚数等极少信息，宁可保持非常克制或标记事实不足，也不能让产品角色替代酒店事实或生成泛化酒店介绍。
- `editorialCopy` 负责解释住宿价值；`proofPoints` 负责快速记忆，正常输出 2—3 个短标签，优先使用真实地点、保护区、景观、空间类型、明确数量或可直接理解的住宿价值。每项只表达一个事实或价值，优先 4—10 个中文字，不写完整说明句，不以“位于、拥有、提供、配备”开头，不把抽象修辞重新塞进标签，也不重复正文完整句。事实只支持 0—1 项时按真实数量保留并记录事实不足，不得凑满；最多可有一个轻量产品角色标签。
- 具体哪一天入住、当天抵达后的情境以及与当天行程如何衔接，由对应 DAY 表达；同一真实酒店事实跨总览与 DAY 出现时必须使用不同角度和粒度。

### COPY-008 特色餐饮

- 特色餐饮是整趟旅行特色餐食的客户代表集，回答“这趟旅途中有哪些彼此不同、值得提前期待的餐饮体验”，不是 Excel 中全部餐饮关键词的集合。只有本次原始资料明确存在且可独立成立的特色餐厅、特殊用餐场景、丛林晚宴、海边晚餐、营地特色餐食或其他真实餐饮形式进入独立板块；普通早餐、午餐、午餐盒和普通酒店晚餐只在 DAY 中简洁说明。
- 餐食若只是另一项主体验的组成部分，不自动升级为独立 Dining Card；例如某主体验括号内“含某餐食”时，除非来源另外把该餐食作为独立特色产品重点说明，否则只留在对应 DAY / Spot。
- 同一 DAY 的相同体验合并证据后只生成一项。同一语义类型跨 DAY 默认只选择一个代表项，优先比较来源突出程度、证据具体度、独立性、场景辨识度、与其他体验的差异、状态清晰度及整程代表性；酒店不同或 DAY 不同本身不足以保留两项。只有两项在真实场景、体验形式或客户价值上有明确重要差异，且来源分别突出时，才允许同类并存。
- 普通 7—10 日产品通常选择约 4—6 项作为软范围；真实内容少则按实际数量展示，高度重复则压缩，不为达到数量凑体验。
- `included/optional_paid/reservation_required/pending` 等状态必须保留，不得因为尚待确认、自费或需预约就直接删除。状态判断整项体验本身的订单状态；体验内部的部分升级消费另收费时，保留局部费用 `sourceEvidence`，不得因此把整项体验降为 pending，也不得误写成升级消费已包含。
- `editorialCopy` 是特色美食、品饮或用餐体验的产品介绍，最终回答“这一顿和普通用餐有什么不同，为什么值得期待”。正文用 1—2 个短句，优先顺序为：餐饮类型或品饮内容 → 怎么吃、怎么喝或怎么品 → 味觉/品饮/用餐方式的特点 → 已确认的特色场景 → 一个直接客户价值。场景感、氛围感和记忆感可以使用，但只能增强餐饮体验本身，不能让风景、情绪或诗性收尾取代吃、喝、品与用餐方式。
- COPY-001 的“先制造向往”在 Dining 中必须由餐饮内容和体验方式本身产生，不能先写风景再补一句餐饮。第一句应以吃、喝、品或明确餐饮类型为语义主体；即使移除场景修饰，客户仍应看懂这是什么餐饮、如何体验及其与普通用餐的差异。
- 优先采用“餐饮动作或内容 → 已确认的体验方式/场景 → 与普通用餐的直接差异或价值”的产品句式。每个分句都应服务于餐饮主体；餐饮信息表达完整后不再另加只负责总结旅程、情绪或记忆的尾句。
- Dining 不承担当天或整趟旅程的收束职责。写清餐饮本身、体验方式、已确认场景和直接价值后立即结束，不需要再总结一天、告别一地或为旅程收尾。
- “有体验感”是让客户理解怎么吃、怎么喝、怎么坐下来体验，以及为什么这顿与普通三餐不同，不是单独制造写景段落。客观事实必须有依据；可基于已确认的餐饮类型、地点、场景与安排做轻量、非承诺性的自然动作和客户价值展开，不要求来源出现完全相同原句。卡片已有 title、location、status，正文不机械重复 DAY 编号、完整酒店名、地点或状态；不得从短名称自行补出具体设施、人物服务、菜单食材、布置动作、烹饪方式、天气天象等可核验现场细节。
- 每张卡必须对应一个明确餐饮形态，不能用酒店大堂、门头、普通树景等无关内容替代。
- 具体哪一天体验、当天如何发生及局部费用边界由对应 DAY 表达；同一真实餐饮事实可跨总览与 DAY 分别表达，但不得整句整段复制。

### COPY-009 全程交通

- 全程交通是整趟旅行主要交通配置的总览。现有字段按五层分工：`usageLabel` 是客户可见的使用范围；`category` 是实际交通产品名称；`serviceLevel`、`seatCount` 与有保证的 `model` 是配置或产品角色短标签；`editorialCopy` 只解释一个核心客户价值；`features` 展示 2—3 个简短配置价值点。标题与标签不得原样重复，某层没有真实信息时可少显示，不能为了结构完整编造。
- `usageSegments` 继续保存内部逐日对应，只作为形成 `usageLabel` 与价值点的依据；客户卡不得显示 DAY 编号或未经整理的逐日路线字符串。使用范围可概括实际城市、区域、保护区或衔接场景，帮助客户理解“主要用在哪里”，但不逐段解释每天 A→B。
- 没有来源时不得自行补座位空间、承载数量、动力、准时性、车型能力、包含状态或精确节省时间；有依据的配置只在当前唯一客户价值或短价值点中表达。`features` 不要求凑满三条，且不能把交通工具百科知识当作本产品配置。
- 具体品牌和车型只有在源数据明确保证时才能承诺；未保证时写同等级实际调度，且统一免责声明只出现一次。
- 每日交通源数据与汇总模块必须逐项对应；源文件存在每日交通但汇总为空时阻止生成，不能隐藏模块。
- 同一真实交通事实可在全程交通总览和对应 DAY 分别表达，但必须分别服务“整程移动配置与品质”和“当天如何发生”，不得整句整段复制。

### COPY-010 每日行程

- DAY 头部固定保留日期、每日主题和服务标签；下方信息区固定为当日行程、体验图片、当日路线、当晚入住/安排、当日用餐、当日节奏。字段无适用事实时可隐藏，但不得打乱其余顺序；每日贴士不显示。
- 正文回答“今天最核心的一段体验怎么展开”，不得只写“前往—参观—返回”。普通 DAY 从真实事实中选择 1 个主体验、最多 1 个辅助体验，用必要移动信息串联并解释为什么值得；结构字段负责完整保存路线、交通、餐食、住宿、Spot、状态与费用边界，正文不逐项复述。
- DAY 文案采用高端定制旅行产品经理视角。相邻 DAY 必须体现 Planner `dayRole` 和真实事实支持的差异，不能批量同义改写同一个地点或“游猎日”。
- `days[].description` 负责整日推进和主次关系；`days[].spots[].description` 只负责对应体验卡，解释该 spot 的内容、方式和价值，不得把整日摘要复制进单项体验卡，也不得改写体验名称、状态或费用边界。
- 同名 spot 跨日出现时，应结合本日 `dayRole` 调整信息重点或保持克制，不得复用相邻日整句；spot 卡不得带入酒店、当日其他活动或整日收束。
- “清晨、午后、傍晚”等可以用于不形成固定钟点承诺的合理时间推进；只有写成“19:30 准时出发”这类具体履约时间时，才必须有订单或已核验依据。百科信息必须压缩进客户的现场体验，不能独立堆知识。
- 相邻 DAY 必须有不同重点，不得同义改写重复；质量失败仅重写被命中的字段或 DAY，未命中模块保持原值。
- 普通体验日优先约120—180字且宜不超过220字，纯转场/返程优先约80—130字；均为软建议，不是自动删除线。只有句子连续堆砌活动、地点、动物、人员资质和设施而没有客户推进/价值，或真实2000px版面已经无法阅读时，才按需局部调整。
- 酒店、特色餐饮和交通事实可在专业总览中表达整趟旅行的配置与整体价值，并在 DAY 中说明当天具体如何发生；这类跨层表达不视为重复，但必须改变角度和信息粒度。禁止整句整段原样重复、两个模块说完全相同的话或为了填满模块重复堆砌。
- 原始资料中有依据的高价值卖点默认保留。品牌审核按“直接保留 → 补充解释 → 调整结构/详略 → 核验事实 → 有明确依据时删除”的顺序给建议；用户明确满意的原文跳过普通品牌改写，只有硬问题可以解除保留锁。

### COPY-011 体验状态同步

- 已含、自费可选、需预约、待确认和仅推荐必须保留真实状态；可成为正文高潮或主图，但不得暗示已经包含或确认。
- 正文、体验卡、图片蓝图、费用包含/不含和待确认列表必须同步；冲突属于事实问题，阻止生成并返回用户，不能靠文案改写掩盖。

### COPY-012 每日贴士停用与历史兼容

- 客户成品和编辑器不再展示每日贴士，也不把它作为 DAY 完整性的必需字段。
- 历史项目中的 `dayNotices/dayNotes` 字段继续兼容读取，不删除、不迁移、不阻断打开或导出；前端渲染时直接忽略。
- 原始资料中的事实、费用、履约、安全或准备提醒仍须进入各自对应的状态、确认流程或最终“注意事项”，不得因为每日贴士停用而丢失。
- 不把历史每日贴士静默拼接进当日行程、当日节奏、体验卡或最终注意事项，避免改变客户原文和信息层级。

### COPY-013 注意事项

- 按实际相关性覆盖行程运营、气候穿着健康、游猎/营地安全、海上活动、证件财物行李、儿童长者和特殊需求。
- 模块心理感受是“这些细节我们已经提前替您想到，也会协助确认”。每条先说明服务团队提前考虑或将协助核对什么，再给客户一个具体准备动作；需要临近出发确认的事项明确由定制师协助，不把责任单独推给客户。
- 服务型语气不能升级为无来源承诺：不得声称已经掌握输入中没有的客户偏好、健康情况或纪念日，也不得承诺未配置的供应商资质、布置、顾问服务或全部项目已确认。
- 标题采用出行准备、健康与安心、当地文化与礼仪、出发前再确认等服务型语义；不要求逐字套用。正文避免连续使用命令式口吻，安全规则改写为跟随向导与现场安排即可执行的安心建议。
- 签证、健康、安全或季节窗口等时效信息必须带权威来源和核验日期；没有依据时只说明定制师将在出发前按最新正式要求协助核对，不输出具体有效期、金额或窗口。
- 未取得权威当前事实时，不输出固定健康要求，也不输出“营地通常提供洗衣、卫星电话或 Wi-Fi”等泛化酒店服务结论；不为了形式完整硬塞所有可能类别。

### COPY-014 费用表达与源数据覆盖

- 费用包含按住宿、交通、门票、司导、餐食、已含体验和服务支持表达客户价值；费用不含按机票、签证保险、小费、个人消费、未购买体验、未注明升级和临时变更费用清晰说明。
- 源文件每一项客户费用必须进入确定性覆盖台账，并与结构化包含/不含逐项、逐数量核对；源文件存在而结构化数组为空、数量减少或内容缺失时阻止生成。
- 文案可改变表达方式，不能合并掉独立费用边界、增加未确认包含项或删除原始不含项；内部成本、底价、利润、公式和供应商备注禁止进入客户结果。
- 可选服务在正文写“可提前预约/协助增订”，同时在费用不含写“当前报价未包含”。

### COPY-015 事实、情绪与承诺

- 主观旅行价值可以有感染力，但“全球唯一、世界第一、最大、奖项、房量、设施、位置、固定活动时间、保证看到的动物、具体人员资质、开放时间、运营规则、车型、房型、菜单”等会形成明确实体事实或客户承诺的可核验陈述，必须逐句有来源依据。来源可以是本次供应商资料、用户确认或按 DATA-001 受控准入且带来源与核验记录的公开资料；搜索摘要、图片、博客、论坛、用户评论、社交平台和百科不单独证明事实。
- “客人会在怎样的空间中停留、这种节奏带来怎样的体感、为什么这项安排值得”等体验化解释，在依附已确认地点、活动、酒店、住宿形态、交通、节奏或服务方式且不改变产品边界时允许使用，不因 Excel 缺少相同原句而自动判为虚构。
- 公开事实研究只补充实体客观属性，不能改变本订单购买内容。房型、包含项、价格、已保证车型、已预订服务和正式状态只能来自 Excel、用户确认、正式供应商确认或确定性配置；即使实体官网提供一般性信息，也不能据此推断本次订单已包含。
- 每个含可核验事实的输出字段保存对应原始事实摘录；一句包含多个独立事实时须有足够依据覆盖，不能用模型常识或想象补全。
- 门禁判断的是一句话是否新增未经支持的客观承诺、履约事实或订单边界，而不是某个词是否出现在 Excel。基于已确认活动作合理体验展开，使用不固定具体钟点的时间推进，对已确认 guided activity 自然表达向导与观察方式，对已确认夜间游猎说明常规探照观察方式，使用“有机会观察”等非保证性动物表达，以及给出不改变订单状态的轻量预约建议，均可接受。
- Program 不得再以游猎、动物观察、向导、徒步、管家、公共空间、泳池、露台/凉亭、房型/住宿空间等类别词未在当前局部 task 中逐字命中为由拒绝整项输出；这些内容是否真实由 Copy 的事实输入、`verifiedFacts`、写作约束和人工审查负责。
- 只有固定钟点、保证看到具体动物或获得某结果、具体人员资质等级、强制预约要求或精确预约期限、具体金额，以及“已包含、已预订、保证使用某房型/车型”等会改变产品事实和客户承诺的表达，才必须在当前目标的订单事实或 `verifiedFacts` 中有明确依据；不能从相邻 DAY、其他模块或模型常识借用。“建议提前咨询/预约，以实际确认为准”属于轻量建议；“需提前预约/必须预约”会改变订单要求，必须有 `reservation_required` 等确定性状态支持。
- 动物、天气、迁徙、渡河、升级、包场和未确认体验不得保证；自然吸引力应采用“值得期待的场景 + 适用窗口（有权威依据时）+ 团队安排 + 温和不确定性边界”。
- 无权威来源 URL 与核验日期时，禁止输出“有效期6个月、费用50美元、某月至某月”等具体时效结论。

### COPY-016 定制师模块

- 仅显示真实配置的个人资料；没有资料时使用明确的非真人默认头像和占位姓名/职位，不编造年限、订单、好评、联系方式或服务纪录。
- 定制师电话与工作微信属于用户配置的个人资料。电话在客户成品中完整展示，工作微信允许自由文本；页面按“姓名/职位 → 联系方式 → 个人介绍”阅读，单项为空只隐藏该项，两项均为空时整行隐藏并自然收缩。
- 隐藏空指标并收缩空间，固定收束语可以使用“让你的旅行 有品质 也有范儿”。

### COPY-017 客户数据隔离

- 客户预览、JSON 和 PNG 均不得出现原始资料标记、审核分数、候选状态、模型提示词/理由、内部路径、来源账本、成本利润和供应商沟通信息。
- 来源摘录、品牌复核问题、改写补丁和规则报告只保存在内部证据中；客户结果通过白名单序列化。

## 品牌判断参考例（不要求逐字模仿）

本节示例用于帮助文案生成与审查理解 `COPY-001/005/007/012/015` 的判断方式，不是固定模板，也不构成事实来源。示例中的地点、季节、设施、活动和服务只有在本次输入有对应依据时才能使用；智能体应迁移“表达结构”，不得复制示例事实。

### 1. 有场景的感染力与空泛形容词

- 参考方向：先写客户能感受到的动作或空间，再解释为何稀缺以及路线如何安排。例如“把清晨黄金时段留给核心体验，而不是长途折返”。
- 反例：连续堆叠“顶级、尊享、非凡、奢华、震撼”，却没有地点、动作、节奏或服务依据。
- 使用环节：文案生成与独立品牌审查；事实不足时缩短表达，不用更多形容词补空。

### 2. 酒店价值表达

- 参考结构：酒店正式身份与有来源的级别/定位 → 所在地点或区域 → 整体住宿质感 → 一至两个有来源的空间、景观、服务或体验锚点 → 对整趟住宿配置的价值。
- 参考方向：“由一组各具辨识度的住宿共同建立整趟旅程的品质感”“让景观、私密性与真实空间体验成为值得提前期待的住宿组成”。
- 反例：“拥有餐厅、泳池、客房、酒吧、健身房”等设施清单，或只写“顶奢酒店、体验非凡”。
- 使用环节：酒店文案生成、官方事实搜索后的受限补充、生成后审查；没有来源的设施和动物场景必须删除或转待确认。

### 3. 每日贴士停用

- 客户成品与编辑器均不显示每日贴士；历史字段仅用于兼容旧项目读取。
- 与当天相关的事实、状态和费用边界继续进入对应固定字段；全程准备事项集中在最终“注意事项”。
- 不得为了复用历史内容，把每日贴士改名后塞入其他模块。

### 4. 自然现象与不确定性

- 参考结构：为什么值得期待 → 有权威依据时写适用窗口 → 团队如何观察和安排 → 温和说明自然结果不作保证。
- 参考表达：“向导会结合当日条件选择观察与守候区域；是否出现具体自然场景仍由真实环境决定。”
- 反例：“保证看到”“必定发生”；也避免只剩“完全取决于自然、概不负责、后果自负”的冷硬免责。
- 使用环节：事实搜索、文案生成、时效检查和人工复核；无权威来源 URL 与核验日期时不得输出月份、金额、有效期等具体数字。

### 5. 自费、可选与待确认体验

- 参考结构：正文可以写吸引力和预约方式，同时以安静状态行写“自费可选/需预约/待确认”，并在费用不含或待确认列表保留同一状态。
- 反例：因为项目有销售吸引力就写成已包含；或因为当前未购买就从正文和图片蓝图中一律删除。
- 使用环节：文案生成、图片蓝图、费用一致性审查和正式导出硬门禁。

## 智能体用途与责任摘要

- 任务规划：按 `COPY-002` 划分模块和输入，只安排事实充分的生成任务；不得改变模块顺序或新增客户页面。
- 事实搜索：只为 `DATA-001/016` 允许的酒店公开事实和权威时效信息补证；酒店事实优先官方，官方缺失时才使用逐页核验、字段受限的受控外部来源；搜索摘要、低可信网页、图片和模型常识不能升级为事实。
- 文案生成：允许决定叙事、结构、客户价值和语气；禁止决定确定性事实、费用、履约和体验状态。
- 生成后审查：逐字段返回问题路径、规则、理由、证据缺口和安全动作；普通问题局部重写，硬问题转用户确认或阻断。
- 输出失败：不允许整份无限重写；新智能体按受控目标修正和复检，普通品牌表达建议可由用户接受为 `user_accepted_suggestion`，硬问题继续阻塞。固定流程的98%修订态只属于冻结基线。
- 最终责任：程序负责结构、白名单与硬冲突，AI 负责受限生成和审查，用户负责事实/风险决定，人工负责品牌审美与独立验收。
